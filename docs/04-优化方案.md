## 1. 维度一 · 采集可靠性

### OPT-1.1 采集链三颗地雷（P0，小~中）

- **现状问题**：
  1. `airmon/collect.py:44-81` `_enrich_and_detect` 用 `as_completed(..., timeout=30)`，一个慢 DNS 域名让 16 并发整批 resolve 抛 TimeoutError 且未捕获 → **该机场本轮采集整体失败**（【审计】§4 R-10）。对 44 机场常态运行这是单点引爆路径。
  2. `airmon/enrich.py:52-53` RDAP"重试"是死代码（`for attempt in range(2)` 体内 `except: break`），注释宣称的 429/503 退避不存在；限流实际全靠 ip-api 45req/min + workers=12 硬扛（【审计】§4 R-11）。
  3. `data/.cache/rdap_cache.json`（约 3.6MB）由多线程无锁全量重写，且无 TTL 永不失效——并发写损坏一次，下次加载即炸（【审计】§4 R-12）。
  4. 叠加项：`resolve` 超时不封顶（【审计】R-13）。
- **建议方案**：① per-future timeout + 失败节点补空列表继续；② 真退避重试（429/5xx 指数退避 ≤2 次）；③ 缓存加线程锁 + 改 JSONL 追加或定期批量落盘 + 90 天 TTL；④ resolve 墙钟封顶。
- **改动量级**：小~中（三处函数级改造，不动架构）。
- **风险**：低。重试会拉长单机场墙钟，需与 OPT-1.2 的超时预算统一设定。
- **优先级**：P0。

### OPT-1.2 采集结果可信化：结构化结果 + 失败语义 + 退出码（P0，中）

- **现状问题**：【审计】§3.2 对 `run.py all`（run.py:902-994）五段流水线的失败语义专析——R-14 ok/fail 统计失真（`_pull_one` 无返回值，"44 成功"可能实际 0 节点）；R-15 超时线程不终止，与 3/5 rescan、4/5 export 读写竞态；R-16 无进程级超时；R-17 退出码恒 0（run.py:1394-1395）；R-18 阶段间无失败传播。【运行】§5.6 确认监控盲区：无按机场聚合的失败率视图。
- **建议方案**：`_pull_one` 改为返回结果对象 `{slug, route, ok, nodes, error, elapsed}`；每轮落盘 `data/last_run.json`（见 OPT-4.1）；退出码分级 0=全好 / 2=有机场硬失败 / 3=有超时；对超时线程改用"写入前检查批次号"或进程池隔离的思路消除竞态；export/report 读快照加 try（【审计】R-7 后半）。
- **改动量级**：中（run.py 主流程改造 + 各采集路线返回值统一）。
- **风险**：中。客户端扫描兜底路径（muniu/wdy 的真实数据源，【运行】§5.4）依赖现有时序，改动须保住"1/5 段 0 节点→2/5 段兜底"的接力语义，建议先补 OPT-5.2 的 store/parse 用例再动。
- **优先级**：P0。

### OPT-1.3 凭证健康度管理（P1，中）

- **现状问题**：凭证类故障全是事后人工发现——【盘点】§4.9 遗留 9 条中 5 条是凭证/通道失效（kuainiao 凭证失效、bywave 需重新注册、muniu 续费、ss-id sub_url、wdy 客户端登录）；【运行】§5.4 显示 jsqpro 101/624 轮 0 节点、yiyuan 82/624 轮间歇；【运行】TL;DR#2 yiyuan 连续断档 7 天无任何告警。另【审计】R-26：`_try_all_panels`（run.py:161-234）对 seeds 逐域名重放真实口令，有触发风控/锁号的反作用——**失败的探测本身会加速凭证死亡**。
- **建议方案**：为每个 slug 维护凭证状态机 `ok / degraded(间歇失败) / expired(连续 N 轮 0 节点或登录失败)`，状态写入 last_run.json 并随轮更新；连续 3 轮 expired 触发 OPT-3.2 告警；登录前先用 `detect_panel` 空凭证探测确认面板类型再提交口令（【审计】§6-P1-8）；airports.yaml 注册表补 `enabled/失效原因/最后成功时间` 字段。
- **改动量级**：中。
- **风险**：低。注意 expired 判定要区分"订阅真失效"与"临时代理问题"（用 OPT-4.3 前置自检排除后者）。
- **优先级**：P1。

### OPT-1.4 Velochron 签名失效兜底（P1，小~中）

- **现状问题**：`airmon/velo_api.py:42-46` 硬编码 `APP_SIGNATURE / APP_VERSION / PANEL`，代码注释自认"若客户端升级导致 403，重装/解包新版本并从其 sig cache 提取新值"（本次抽查原文属实）；【盘点】§4.2 部署指南把"Velochron 403=X-App-Signature 过期需更新 velo_api.py 常量"列为常规故障排查项——意味着这是**必然复发**的故障，目前处置=改源码。【审计】R-27 同列此风险。
- **建议方案**：三要素外置到 credentials.yaml 的 per-airport 覆盖字段（代码默认值保留兜底）；403 且响应含签名拒绝特征时：a) 自动降级到 dpapi 路线（airmon/dpapi.py 已具备，缓存 >48h 自动 GUI 刷新，【盘点】§4.9）；b) 触发"签名失效需人工提取"告警（不自动逆向，人工步骤写进告警文案）；c) 恢复后自动切回。
- **改动量级**：小~中（velo_api.py + run.py `_pull_one` 优先级链 run.py:380-530 增加降级分支）。
- **风险**：低。dpapi 路线依赖本机 Velochron 客户端登录态（【盘点】§4.9），告警文案须说明此前提。
- **优先级**：P1。

### OPT-1.5 QQT 客户端常驻依赖治理（P1，中）

- **现状问题**：【盘点】§7 隐患5——persistent 路线（quqiuquan）依赖 qqt.exe 常驻自持登录态，"未运行即整链路静默跳过（有日志提示但无告警升级）"；【运行】§5.5 显示"客户端未运行"是高频信号（近 112 轮 lingdian 222 次≈2 行/轮、velochron 136、letsvpn 112、quqiuquan 112），目前完全靠人工开客户端。【盘点】§4.8：QQT 无客户端化差最后一环签名（进度 95%），短期不能指望。
- **建议方案**：分四步——a) 客户端型机场的"客户端未运行"从日志噪音升级为独立告警类别（连续 2 轮未运行即报）；b) 计划任务轮前增加"客户端进程预检+可选自动拉起"（自动拉起 GUI 有会话/前台焦点不确定性，建议**默认只告警**、拉起做成配置开关）；c) persistent 连通探针从分钟级全堆内存扫描改 TCP 连接表判断（【审计】R-35）；d) QQT 签名逆向保持研究支线，**不阻塞常态化**。
- **改动量级**：中。
- **风险**：中。自动拉起若与 `_do_scan_memory`（run.py:256-349）的启动逻辑并发会复现【审计】R-15 的"同时二次启动同一客户端"问题，实现时须复用同一启动器。
- **优先级**：P1。

### OPT-1.6 回退链降噪与路由 skip 标记（P1，小）

- **现状问题**：【运行】§5.4——muniu manual-url 路线 584/624 轮恒 0、wdy v2board 路线 529/624 轮恒 0，真实数据由客户端扫描阶段兜底；"⚠ 0 节点"警告 332 行≈3 行/轮，99% 来自这两家的固定兜底路径。【运行】§5.5：登录失败行绝大多数是回退探测的设计噪音（bywave/dovex/hhy 等"每轮恰好 1 行"）。噪音把真失败淹没，也浪费每轮 300s join 预算。
- **建议方案**：credentials.yaml 支持 `skip_routes: [manual-url]` 类标记（muniu/wdy 配置主路由为客户端扫描、跳过已知恒 0 的直连探测）；skip 通道每 7 天强制试运行一次以探测通道是否恢复；日志把"设计内回退探测"与"计划外失败"分通道输出。
- **改动量级**：小。
- **风险**：低。最大风险是把"暂时失效但会恢复"的通道锁死——强制试运行 + 状态机（OPT-1.3）双保险。
- **优先级**：P1。

### OPT-1.7 内存扫描路线可靠性（P1，中）

- **现状问题**（14 个客户端型机场的数据源，【运行】§5.3 scan-memory 行）：① tasklist 输出 GBK 解码 bug 三处实现不一致（memsan.py:81-101 / run.py:266-275 复制的 `_find_pid` / netmon.py:124-145），中文进程名按 UTF-8 解必失败 → 中文名客户端永远找不到 PID（【审计】R-21）；② winclient.py:196-211 WSL 路径 bug，Windows 原生 Python 静默 0 结果（【审计】R-24）；③ memsan.py:354-364 密码启发式"取最后一个"错配，快照密码字段不可信（【审计】R-25）；④ 单客户端扫描最长 ~200s 且每轮全量 DNS+RDAP 富化（【审计】R-34）；⑤ 内存扫描误报防护（extract_nodes 黑白名单）未落地，已有 DeepSeek DNS 缓存误报实锤（【盘点】§7 隐患6、【盘点】§4.6）。
- **建议方案**：tasklist 解码统一为 `_decode_bytes(b, ["gbk","utf-8"])` 并收敛到单一 airmon.winproc 模块（为 OPT-5.1 铺路）；修 WSL 路径 bug 或干脆下线该路线（winclient 与 clientscan 功能重叠）；密码错配修复或对内存扫描来源直接弃用密码字段（见 OPT-2.5）；扫描改"首轮全扫、后续只 diff"（【审计】§6-P2 建议）；黑白名单落地。
- **改动量级**：中。
- **风险**：中。这是 14 家机场的命脉改动，逐家验证（每家跑一轮 scan-memory 对照节点数）后再进计划任务。
- **优先级**：P1。

## 2. 维度二 · 数据治理

### OPT-2.1 快照保留与清理策略（P1，中）

- **现状问题**：【运行】§2.5——44,238 文件/2,196.7MB，增速 550 文件/天、28MB/天（≈0.85GB/月，1 年≈10GB），无任何轮转归档；【审计】R-33 同判；冗余源头之一是 rescan 阶段在每轮尾段重写多数机场快照（同轮 2 份、内容高度相似，【运行】§2.5/§5.2）。
- **建议方案**：三级保留——最近 48h 全量保留；30 天内每机场每天保留最后 1 份；更早的每周 1 份并 zip 归档（归档不删除，移入 `data/_archive/<YYYY-MM>/`）；`run.py prune` 独立命令、支持 `--dry-run`；rescan 改原地更新或同轮去重（与 OPT-2.2 联动）。执行后 2.2GB 活跃区预计缩到 300MB 内（【审计】§6-P1-7 同口径）。
- **改动量级**：中。
- **风险**：中。`diff_latest` 依赖"最近两份快照"语义（airmon/store.py:41-54），清理器必须保证每个机场活跃区永远留有 ≥2 份近期快照，否则 diff/churn 断流；归档只压缩不删，可回放。
- **优先级**：P1。

### OPT-2.2 churn 去污染（同轮自差）+ 0 节点 diff 门槛（P0，小~中）

- **现状问题**：① `diff_latest`（airmon/store.py:41-54）比较"最近两份快照"，而同一轮内 pull 与 rescan 先后各落一份 → churn 统计被同轮自差污染，wdy −587/+0 单边事件疑似 rescan 增删不对称的产物（【运行】§4.4）；② 0 节点快照直接进 diff → 误报"全部节点消失"（【审计】R-19）；③ 与 OPT-3.1 的空块问题同根。
- **建议方案**：快照 meta 增加 `run_id`（批次号），diff 跳过同 run_id 的相邻快照或改按天聚合比较；`cur.nodes==0` 时 diff 返回 `{status:"collect_failed"}` 语义而非节点增删（采集失败归 OPT-3.1 的 failure 告警类别，不产出 churn）。
- **改动量级**：小~中。
- **风险**：低。注意 deploy 方案 B 若上线（watch 每 300s 写 muniu-ninja）会引入第二写入源，run_id 机制天然可区分（【运行】§7.2 G4 已预警双源污染）。
- **优先级**：P0（是告警可信的前提，随阶段一与 OPT-3.1 一起做）。

### OPT-2.3 run.log 轮转与编码统一（P1，小~中）

- **现状问题**：① run.log 21MB/332,024 行无轮转（【盘点】§7 隐患1、【运行】§5.1），≈8MB/月持续增长；② **同文件双编码混写**：auto_run.bat:6,8 的 cmd `echo` 行以 GBK 写入、python 输出因 PYTHONIOENCODING=utf-8（auto_run.bat:5）以 UTF-8 写入，任一编码读都有一段乱码（【审计】§3.4 机理分析、【运行】§5.1 实测"GBK+UTF-8 混编"）；③ 全项目 print 直写无日志框架（【审计】R-30）。
- **建议方案**：print → logging + RotatingFileHandler（建议 10MB×5 份）统一 UTF-8；auto_run.bat 去 echo 或将 echo 改向独立 bat.log 并 `chcp 65001`；历史 run.log 按月切割归档。**改动触及在用调度链，须在场验证一轮后再离开**（本轮任务约束禁改，列入阶段三执行）。
- **改动量级**：小~中。
- **风险**：低。唯一注意点：run.log 是【运行】§5 全部统计口径的数据源，切换后旧口径脚本失效——正好借 SQLite 底座（OPT-2.4）替代文本日志聚合。
- **优先级**：P1。

### OPT-2.4 历史数据底座：SQLite/Parquet 取舍（P1，中）——仪表盘历史趋势的数据底座

- **现状问题**：当前"数据库"就是 47 个目录 × 44,238 个 JSON 文件（【运行】§2）；任何跨机场/跨时间聚合都要全目录扫 JSON（【运行】附录 A 的聚合就是人工 PowerShell 完成的）；`diff_latest` 只看最近两份，历史趋势无从查询。T5 仪表盘的"历史趋势"迭代没有可查底座。
- **取舍分析**：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **SQLite（单文件运营库）** | Python 内置 sqlite3 零新依赖；事务+索引；按 (airport, ts) 主键 upsert 天然幂等；仪表盘/SQL 直接查；WAL 模式可边写边读 | 大范围分析扫描弱于列存；并发写需注意（单写者即可满足本场景，写入点单一） | **主选** |
| **Parquet（列存归档）** | 压缩率高、分析快、pandas 生态好 | 需新依赖（pyarrow/duckdb）——本项目已有缺依赖前科（requirements.txt:1-2 仅两项，【审计】R-23）；行级更新不便；直查需额外引擎 | 月度归档分析层，P2 可选 |
| 快照 JSON 原样保留 | 原始事实源，可追溯可重放导入 | 不适合查询 | 保留为唯一事实源 |

- **建议方案**：建 `airmon/tsdb.py` + `data/airmon.sqlite`（WAL），四张最小表：
  - `runs(ts, run_kind, ok_airports, fail_airports, total_nodes, huawei_hits, elapsed_s, exit_code)`
  - `airport_runs(ts, airport, route, nodes, ok, error, elapsed_s)`
  - `node_timeseries(ts, airport, node_key, server, port, protocol, resolved_ip, rdap_network, rdap_country, huawei_flag)`，主键 (airport, node_key, ts)
  - `alerts(ts, airport, kind, severity, fingerprint, payload)`
  导入器在 `run.py all` 末尾调用，以快照文件名 ts 为主键成分幂等 upsert；**导入失败 try 包裹，绝不影响采集主流程**；SQLite 是派生物，可随时从快照全量重建。
- **改动量级**：中。
- **风险**：中。双写不一致是主要风险 → 用"快照 JSON 唯一事实源 + 幂等重建"原则兜底；表结构落地前与 T5 的 docs\05-仪表盘设计.md 对齐一次，避免仪表盘二次返工。
- **优先级**：P1（阶段三，先于仪表盘历史趋势迭代）。

### OPT-2.5 敏感数据落盘治理（P0 部分，中）

- **现状问题**：① 快照即"节点密码+密钥仓库"：velo_api `_AERO_FIELDS`（velo_api.py:49-53，含 edge_psk/aead_key/resume_ticket/password）、memsan.py:257-366、nodepage.py:69、winclient meta 全部把敏感字段写进 data/ 快照（【审计】R-4）；【运行】§3.4 实测 raw.password 为明文 UUID，47 目录级联暴露；② 订阅 token 进 run.log 多处（autoscan.py:62-65、run.py:459/579/641-642，【审计】R-5）；③ .gitignore 未覆盖根目录敏感研究产物：velo_native_nodes.json(973KB)、velochron_sub.yaml、*_sub.yaml、qqt_nodes_dump.json、velo_secure2/、seeds.txt（【盘点】§7 隐患2）——`git add .` 即泄漏；④ 与 README 隐私承诺（【盘点】§4.1"勿进公开仓库"）存在承诺-现实差。
- **建议方案**：a)（P0，半天）.gitignore 补全上述条目 + `git log` 历史检查；b)（P1）快照落盘前对 password/psk/token 类字段统一脱敏或哈希（该字段对华为检测无贡献，【运行】§3.4 已确认）；c)（P1）日志统一脱敏函数处理 `token=...`/sub_url；d)（P1）data/ 与 credentials.yaml 文件 ACL 收紧到当前用户。
- **改动量级**：中。
- **风险**：中。**脱敏不能误伤 OPT-3.5 聚合订阅**（自用订阅需要完整节点配置）→ 原则：落盘快照脱敏；聚合订阅在内存中从订阅原文生成、产物单独加密存放或完全不落盘。
- **优先级**：.gitignore=P0；脱敏/ACL=P1。

## 3. 维度三 · 监控能力补齐（README 阶段4）

### OPT-3.1 告警可信化：空块修复 + 分级 + 降噪（P0，小~中）

- **现状问题**：alerts.log 15,664 块中 83.9%（13,142 块）只有头行；根因代码级核实——`diff_latest()`（store.py:41-54）只要有 ≥2 份快照就返回 truthy dict，`emit()`（alert.py:13-31）changes 为"全空字段的 dict"时不会提前返回，调用点 run.py:378 每轮每机场都写块（【运行】§4.2，本次源码抽查属实）；近 14 天 2,564 块 ≈183 块/天纯噪音，**当前不可直接用作告警源**（【运行】§4.5）；且 alert 无去重/限流/分级（【审计】R-20）。
- **建议方案**：① 一行级修复：`diff_latest` 在 `not added and not removed and prev_findings==cur_findings` 时返回 None（【运行】§4.2 给出的修复方向，与 OPT-2.2 一起做）；② emit 重写为 severity 分级：华为命中=high、采集失败=high、churn 单事件 >50 或池变动 >20%=medium（阈值取【运行】§4.4 大事件口径：单事件 >50 共 428 次，可设阈值）、其余=info 不落盘；③ 指纹去重：`hash(airport+kind+evidence)` 24h 抑制；④ 采集失败本身作为一类告警接入（现在只有华为命中才 emit，【审计】§6-P1-6）。
- **改动量级**：小~中。
- **风险**：低。修空块预计日志量 −84%（751KB→约 120KB，【运行】§4.5），阈值告警可能漏掉"缓慢失血"型 churn——保留每日 churn 汇总一类 info 报表兜底。
- **优先级**：P0（两周三件套之首）。

### OPT-3.2 Telegram 告警通道（P0，小）

### OPT-3.3 机场陈旧度告警："X 小时无新快照"（P0，小）

### OPT-3.4 节点级探活（README 阶段4，P2，中~大）

- **现状问题**：README 阶段4"探活"未做（【盘点】§4.1）；但 2,611–2,720 节点（【运行】§5.6 final 口径）全量高频 TCP 探活的连接规模与对机场服务端的可见性都不可忽视；且内存扫描路线 protocol 恒 unknown、节点名 node-<port>（【运行】§3.4），探活结果的可解释性受限。
- **建议方案**：分两步——v1 抽样探活：每机场抽 N 个节点（如 10 个，固定+随机结合）做 TCP connect 探测（超时 3s，纯连接不发业务流量），结果写入 OPT-2.4 的 node_timeseries；v2 按需探活：只对华为命中节点与聚合订阅（OPT-3.5）在用节点探活。**不做 2600+ 全量实时探活**。
- **改动量级**：中~大。
- **风险**：中。探活是对机场服务端的主动连接行为，保持低频抽样（每天 1~2 轮）即可，避免触发风控波及采集通道本身。
- **优先级**：P2。

### OPT-3.5 聚合自用订阅（README 阶段4，P2，中）

- **建议方案**：前置小改造：解析阶段把原始节点 URI/配置片段存入快照 raw（不改已有快照，只对新快照生效）；聚合订阅从"最新可用快照的 raw 原文"拼装，不从 node-<port> 重建；产物本地生成、加密存放或不落盘（按需生成）；明确"仅自用、不外发"边界。
- **改动量级**：中。
- **风险**：中。泄露面扩大是主要风险，与 OPT-2.5 脱敏原则对齐（落盘快照脱敏、订阅产物单独保护）。
- **优先级**：P2。

### OPT-3.6 按基础设施簇聚合告警与报表（P2，小~中）

- **现状问题**：【盘点】§4.6 实测 44 品牌≈30~32 个实际运营商：白标簇 llguanglisf.com 3 品牌（speedcat/qingyunti/fastlink）、bilibilitutu 簇 2 品牌（hhy+lingdian 共享租户前缀）、moe233 簇、飞鸟家族 3 品牌、muniu 双产品线；【盘点】§6 明确建议"按基础设施簇聚合告警比按品牌更有意义"。现状告警按机场一告一，同源事件会重复轰炸（如 muniu/muniu-ninja 同面板，【运行】§4.3 两者命中线索相同）。

## 5. 维度五 · 工程化

### OPT-5.1 run.py 巨石拆分（P2，大）

- **现状问题**：run.py 1399 行/24 子命令；`_find_pid` 在 run.py:264-275 与 :742-753 复制两份；`_do_scan_memory`（:256-349）与 cmd_scan_memory（:731-849）流程重复；`report --pull`（:884-900）重复 cmd_all 的 1/5+3/5 段（【审计】R-28）。三处复制正是 R-21 编码 bug "三处实现不一致"的温床。
- **建议方案**：四包拆分——`airmon/cli.py`（argparse）、`airmon/pipeline.py`（五段流水线）、`airmon/ops_memory.py`（scan-memory 族）、`airmon/ops_config.py`（add-airport/set-*）；`_find_pid` 收敛到 airmon.winproc（顺带终结 R-21）。**分两步**：先抽公共函数消重复（低风险）→ 再拆文件（需 OPT-5.2 测试集先行）；每步全 24 子命令冒烟。
- **改动量级**：大。
- **风险**：中。拆分期间回归风险最高的一件事，故排在测试集与告警体系之后（阶段四）。
- **优先级**：P2。

### OPT-5.2 最小测试集（P1，中）

- **现状问题**：全项目 0 个测试文件（【审计】§1/R-29）；R-10/R-11/R-19 这类"注释宣称与实现不符"的 bug（【审计】R-31）没有测试根本拦不住。
- **建议方案**：pytest 四模块起步 ~40 用例——parse.py（每 scheme 一个 fixture）、detect.py+huawei.yaml（含 asn 136958 误报样例、hwcloud 裸子串样例，【审计】§5.2）、store diff 门槛（0 节点/空 diff/OPT-2.2 的 run_id 语义）、enrich（缓存锁、退避重试）；fixtures 一律脱敏合成数据，**禁止真实凭据/真实订阅片段入测试**。
- **改动量级**：中。
- **风险**：低。
- **优先级**：P1（是 OPT-5.1 与 OPT-1.x 改造的安全网，先于拆分）。

### OPT-5.3 配置与机密分离 + 名单单一事实源（P1，中~大）

- **现状问题**：① credentials.yaml 明文 45 账号无任何保护（【审计】R-1，config.py:29-54 直读，本次抽查属实）；② add-airport/set-sub CLI 传密码进 argv（run.py:1371,1383，【审计】R-2）；③ 三个写命令非原子重写 credentials.yaml——写一半崩溃=45 个机场全拉不动（【审计】R-3）；④ **名单三处不一致**：airports.yaml 13 条目（3 个 enabled:false）、credentials.yaml 45 slugs、data/ 47 快照目录（【运行】TL;DR#10、【盘点】§7 隐患3/4）——`add-airport` 从不回填 airports.yaml，名册实际散落在 credentials.yaml。
- **建议方案**：a) 名单统一：airports.yaml 收编为唯一注册表（45 slug 回填、含 route/enabled/失效原因），credentials.yaml 只留机密字段；一次性迁移脚本 + `run.py list` 前后对照验证；b) credentials.yaml 写入统一走 tmp+rename 原子写 + 时间戳备份；c) CLI 密码改交互输入或环境变量提示，禁止 argv 传明文；d) 文件 ACL 收紧；e) 可选 Windows Credential Manager（P2）。
- **改动量级**：中~大。
- **风险**：中。名册迁移必须保证 `_pull_one`（run.py:380-530）读取路径兼容——迁移后先以 `--airport` 单机场验证再放开全量。
- **优先级**：P1。

### OPT-5.4 依赖与交付卫生（P0 一行 + P2 归档）

- **现状问题**：① requirements.txt 仅 PyYAML+requests 两项（本次抽查属实），而 velo_api.py:108 `from cryptography... import AESGCM` 未声明 → 全新监控机部署 velochron 路线直接 ImportError（【审计】R-23）——这直接违背"做稳"（部署可复制性）；② deploy/ 方案 B 上线前置缺口：G2 物料未就位、G3 Dockerfile `COPY . /app` 无 .dockerignore 会把 credentials.yaml（34 个订阅 token）与 2.2GB data/ 打进镜像（【运行】§7.2，高危）；③ 根目录 28 个一次性研究脚本 + 34 组研究数据与在用代码混放（【盘点】§3.4/3.5，可归档）。
- **建议方案**：requirements.txt 补 `cryptography>=42`（一行，P0）；dev-requirements 声明 pytest；deploy 上线前必须补 .dockerignore（排除 data/、run.log、credentials.yaml、client-data/、velo_secure2/）并就位物料（G2/G3 是上线硬门槛，【运行】R9）；根目录研究痕迹移 `archive/`（P2，注意其中敏感文件按 OPT-2.5 处理）。
- **改动量级**：小（requirements/.dockerignore）/中（归档）。
- **风险**：低。
- **优先级**：cryptography=P0；.dockerignore=随 deploy 上线前置；归档=P2。

## 6. 维度六 · 华为关联检测增强

> 背景基线：检测链路数据面完整（server→_resolved_ips→_rdap→findings，【运行】§3.3）；当前服役华为云 CDN=0，最有价值信号是 13 块华为命中（muniu/muniu-ninja/chaoyue/speedcat/quqiuquan，【运行】§4.3）+ 3 处 IaaS 残存（【盘点】§4.6）。增强方向 = 降误报、补漏报、立金标准。

### OPT-6.1 误报治理（P1，小）

- **现状问题**（【审计】§5.2）：① huawei.yaml:25 的 asn 136958 实为**联通广东**，纯联通 IP 一律 medium 判华为——把"华为云租用联通线路"泛化成"联通=华为"；② CIDR 18 段自认部分非华为（huawei.yaml:34/:43 注明）；③ huawei.yaml:55-58 裸子串 `hwcloud`/`hwcdn`/`agconnect` 会命中华为云客户域与第三方域（high 级误报）；④ collect.py:273-294 全文域名正则把"页面提到华为云文档"也记为 finding，语义稀释；⑤ 内存扫描输入本身带噪声（【盘点】§4.6 DeepSeek DNS 缓存误报实锤）。
- **建议方案**：① asn 136958 降为辅助位（仅当 rdap_name 同现才升级）或移除；② 裸子串改正则锚定（`(^|\.)hwclouds?[-.]`、`(^|\.)agconnect`）；③ 全文正则 finding 加 kind 区分（page_mention vs node_evidence），报表默认只计后者；④ cidr 命中 finding 文案附"该段含非华为地址"复核提示。
- **改动量级**：小。
- **风险**：低，但**必须过 OPT-6.3 回归集**：改动后【运行】§4.3 的 13 块真实命中须全部仍命中。
- **优先级**：P1。

### OPT-6.2 漏报补路（P1~P2，中）

- **现状问题**（【审计】§5.3）：① `check_string`（维度4 软件字符串）在主采集流程无任何调用点，scan_text 闲置——节点 raw 里的 SNI/ws_path/host 不走检测；② ASN 维度输入质量差：RDAP 路径 asn 常空、解析靠 remarks 含"AS"子串，兜底 ip-api 限流+明文（R-11/R-6b 连坐）；③ 域名维度只查节点 server，CNAME/NS 链路只在 recon 命令里查（且 recon 的 `_dig` 中文 Windows 下 CNAME 假空，【审计】R-36）→ `cdnhwc*` 类 CDN 边缘命中依赖人工单独跑 recon。
- **建议方案**：① scan_text 接入节点 raw 富集（SNI/ws_path/http host 入检测，快照体积增加与 OPT-2.1 保留策略联动）；② rdap 解析改进 asn 提取；③ recon._dig 修复 GBK 输出解析（与 OPT-1.7 的 winproc 收敛同族改动）；④ pull 流程对命中 cidr/域名维度的可疑域名自动触发单点 recon 深查（把 recon 从"想起来才跑"变成检测链一环）。
- **改动量级**：中。
- **风险**：中。raw 富集放大快照体积（与 OPT-2.1 对冲）；深查要限频。
- **优先级**：①③=P1，②④=P2。

### OPT-6.3 检测回归金标准与置信分级（P1，小）

- **现状问题**：检测引擎无回归手段——每次调签名/阈值都靠全量重跑人眼比对；而现成金标准就在手里：alerts.log 的 13 块华为命中（账号注册 IP + 落地网段维护人 + ASN 三重印证，【运行】§4.3）与 2026-09-17 的 897 唯一 IP 复扫=0 华为基线（【盘点】§4.6）。
- **建议方案**：把 13 块命中证据（脱敏后）+ 联通误报样例 + hwcloud 子串样例做成 detect fixtures 回归集，接入 OPT-5.2 测试集与 CI；finding 增加 confidence 复核注记；报表按簇聚合视图（联动 OPT-3.6）。
- **改动量级**：小。
- **风险**：低。
- **优先级**：P1。

## 7. 分阶段落地路线图

> 排序原则：先让"失败可知、告警可信"（阶段一二），再治数据底座（阶段三），然后补工程安全网（阶段四），最后做全能力面（阶段五）。P0 项全部落在前两个阶段。
> 仪表盘衔接：T5 的 MVP 并行交付中（写作时点未落盘）；阶段一即可用 `run.py status`（OPT-4.1）顶替临时看数需求，阶段三设接线检查点。

### 阶段一（第 1–2 周）「告警可信三件套」——目标：坏了 30 分钟内知道

| # | 事项 | 对应 |
|---|---|---|
| 1 | 空块修复 + 0 节点 diff 门槛 + 告警分级/去重/阈值 | OPT-3.1 + OPT-2.2（【运行】R1/R2/R7 前半） |

**验收**：连跑 3 天，TG 只收真告警（华为命中/大额 churn/采集失败/陈旧）；alerts.log 空块率 <5%；人为杀掉代理进程，30 分钟内收到一条可理解的告警。

**验收**：pytest 绿；13 块华为命中回归全过 + 联通样例不再误报；airports.yaml=唯一名册且 credentials.yaml 原子写。

- **依赖链**：OPT-3.1 → OPT-3.2 → OPT-4.4 告警展示；OPT-5.2 → OPT-5.1；OPT-2.4 → 仪表盘历史趋势；OPT-4.3 → OPT-1.3（排除代理假阳性）。
