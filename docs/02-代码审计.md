# 02 · 代码审计报告：airmon 包与 run.py

- 审计对象：`airmon/` 23 个 Python 模块、`run.py`（1399 行）、调度入口（`auto_run.bat` / `run_admin.bat` / `monitor.py`）、`deploy/`、`signatures/huawei.yaml`、`requirements.txt`
- 审计方式：纯静态审读（逐文件 read + 定向 grep），**未运行任何 run.py 子命令、未联网**
- 隐私约束：本文不复制任何 credentials.yaml / airports.yaml 中的口令、订阅 token、节点密码；敏感处一律以 `文件:行号` 指位
- 审计人：code-auditor（jichang-monitor-opt / t2）

## 1. 结论摘要

| 维度 | 结论 |
|---|---|
| 整体判断 | 原型质量：功能覆盖面广（订阅直抓/登录/内存扫描/DPAPI/网络监控/UI 自动化五条采集路线都有实现），但**异常处理普遍"吞掉+打印"**，失败不可观测、不可重试、不可告警，直接常态化跑 44 机场会在"静默 0 节点"上翻车 |
| 最高风险 | ① 敏感数据落盘面广（节点密码/edge_psk/aead_key/auth_token/订阅 token 进 `data/` 快照与 run.log）；② `enrich.rdap` 重试是死代码 + RDAP 磁盘缓存并发写无锁；③ `_enrich_and_detect` 30s 总超时未捕获会炸整批采集；④ `run.py all` 的"成功/超时"统计失真（崩溃线程计为成功） |
| 规模基线 | data/ 50 个机场目录、44,248 个快照 json、2.2 GB，无任何清理轮转；run.log 20.3 MB 无轮转；credentials 约 45 个账号、34 条 sub_url |
| 测试 | **全项目 0 个测试文件**（递归搜 `*test*` 目录为空）；requirements.txt 缺 `cryptography`（velo_api/DPAPI 解密必需） |

风险编号约定：P0=安全/会炸主流程，P1=可靠性/可维护性硬伤，P2=性能与增长。

## 3. run.py 深度审读

### 3.1 命令面：实测 24 个子命令

任务书预估"28 个子命令"，实测 argparse 注册 **24 个**（run.py:1245-1392）：`scan-existing, list, collect, ingest-profile, diff, pull, ingest-page, scan-client, ingest-cookie, watch, scan-win-client, scan-clients, scan-persistent, scan-memory, monitor-net, auto-scan, all, report, export, rescan, recon, add-airport, set-sub, set-client`。

命令分组：
- **只读/展示**：`list`（run.py:51-105，合并 credentials 与 airports 展示最新快照统计）、`diff`、`report`
- **直连型采集**：`collect`、`pull`（核心调度，run.py:532-562）
- **摄入类**：`ingest-profile`、`ingest-page`、`ingest-cookie`、`watch`（run.py:603-628，mtime 轮询落盘 profile）
- **客户端型取证**：`scan-win-client`、`scan-client`、`scan-clients`、`scan-memory`、`scan-persistent`、`monitor-net`、`auto-scan`
- **离线加工**：`rescan`、`export`（run.py:996-1033，导 CSV utf-8-sig）、`recon`、`scan-existing`
- **配置写入**：`add-airport`（run.py:1036-1104）、`set-sub`（:1107-1139）、`set-client`（:1142-1179）——三者都直接重写 credentials.yaml
- **全流程**：`all`（run.py:902-994）、`report --pull`（:884-900，与 all 逻辑重复实现）

### 3.2 `run.py all` 五段流水线实现（run.py:902-994）

```
=== 1/5 拉取所有机场 (run.py:910-921) ===
  遍历 credentials.yaml 全部账号，逐个起 daemon 线程跑 _pull_one，t.join(300)
  超时 → 打印 [跳过] 并 fail+=1；否则 ok+=1
=== 2/5 客户端型机场内存扫描 (run.py:923-955) ===
  收集 credentials+airports 里带 client.core_process 的机场（checked 集合防重复），
  顺序调用 _do_scan_memory（run.py:256-349）：
    tasklist 找 pid → 没有 Popen 启动 GUI（30×2s 轮询）→
    18 轮 × (sleep 10s + collect_memory_scan 全堆扫+富化)，节点数连续3轮差≤2 判稳定 →
    store.save(best_snap) → 默认 taskkill /F 关闭 GUI+Core（keep_alive: true 则保留）
=== 3/5 补全落地IP归属 (run.py:957-963) ===
  遍历 data/*/ 全部目录，rescan_airport 读最新快照→逐IP补 rdap→另存新快照
=== 4/5 导出 CSV (run.py:964-965) ===
  cmd_export(Namespace(airport=None, out=args.out))：最新快照拍平，逐节点逐IP
  重跑 detector.scan_ip_record 打华为标，写 data/nodes_export.csv（utf-8-sig）
=== 5/5 生成报告 (run.py:966-968) ===
  report_mod.generate(None) → data/report.md
末尾汇总打印机场数/节点数/华为命中（run.py:970-994）
```

**失败语义专析（核心发现）**：

1. **R-14 · ok/fail 统计失真（P1）**：`_pull_one` 无返回值，1/5 段的 `ok+=1` 只表示"线程 300 秒内 join 成功"。三种情况都被计为"成功"：a) `_pull_one` 内部打印 `[失败]/[跳过]` 后正常 return；b) `_pull_one` 未捕获异常导致线程崩溃（如 :446 `cred["email"]` 缺失时的行为依赖内层 try 覆盖面）；c) 实际抓到 0 节点。即 **`all` 的成功数与真实采集成功率无关**，44 机场可能"44 成功、实际 0 节点"。
2. **R-15 · 超时线程不终止（P1）**：`t.join(300)` 只是放弃等待，daemon 线程继续运行。超时的机场线程可能在 2/5~5/5 段进行中才完成 `store.save`——与 3/5 rescan（读最新快照）、4/5 export（读最新快照）形成读写竞态；若该线程走到 `_do_scan_memory` 兜底，还会在 2/5 段**同时二次启动同一客户端 GUI**（与主流程 `_sp.Popen` 冲突、互相 taskkill）。
3. **R-16 · 无进程级超时（P1）**：线程超时只能放弃不能杀（Python 无线程 kill），卡死的 requests 没有全局兜底——`login.py` 各调用 timeout 有传（30s 量级），但 `_do_scan_memory` 等待循环最长 180s+30×2s，叠加以 44 机场串行 join，单次 `all` 理论墙钟可达数小时；`monitor.py` 默认 3 小时间隔会被单轮耗时吃满。
4. **R-17 · 退出码恒 0（P1）**：`main()` 对 `args.func(args)` 无 try/except、无 exit code（run.py:1394-1395），2/5~5/5 任一阶段抛未捕获异常会直接崩溃退出（非 0），但"部分机场失败"永远是 0——调度方（auto_run.bat / monitor.py / 任务计划）**无法用返回码区分好坏**。
5. **R-18 · 阶段间无失败传播**：3/5 rescan 返回 None 静默 continue（run.py:961-963）；4/5 export 对 `store.load(snaps[-1])` 无异常保护，一个损坏快照 json 会炸掉整个导出阶段（快照非原子写，见 R-7）。

### 3.3 配置写入命令的风险

- **R-2 · CLI 密码入进程命令行（P0）**：`add-airport --password`、`set-sub --password`（run.py:1371,1383）把口令放 argv，进程列表/.shell history 可见；写入 credentials.yaml 仍是明文（config.py:29-54 直读，无环境变量/keyring 支持）。
- **R-3 · 非原子重写 credentials.yaml（P1）**：三个写命令都是"读全量 → yaml.dump 全量回写"（run.py:1062-1063,1086-1087,1132-1133），无 tmp+rename、无备份；写一半崩溃/断电 = 凭证文件损坏，45 个机场全部拉不动。

### 3.4 调度入口

- `auto_run.bat`：`python run.py all -v >> run.log 2>&1`（auto_run.bat:7）——**追加无轮转**；且 bat 的 `echo` 行（:6,:8）由 cmd.exe 以 ANSI/GBK 写入，python 输出因 `PYTHONIOENCODING=utf-8`（:5）+ main() 强制 reconfigure（run.py:1232-1240）是 UTF-8——**同一文件两种编码混写**，用任一编码读都会出现一段乱码（run.log 乱码的机理）。`:3-4` 硬编码本机代理 `http://[::1]:7890`，代理不在线则全部外联失败（单点）。
- `run_admin.bat`：写死 0dcloud 路径 + 20s 固定等待（run_admin.bat:4-6），演示脚本性质。
- `monitor.py`：循环 subprocess 跑 `run.py all`（monitor.py:31），`returncode==0` 判断了但**没有对失败做任何事**（monitor.py:36,64-66），无重叠保护（单轮超 3h 会背靠背连跑）、无告警、无日志落盘。

### P0/P1 可靠性

| # | 风险 | 位置 | 说明 |
|---|---|---|---|
| R-10 | **30s 总超时炸整批** | collect.py:44-81（`as_completed(..., timeout=30)`） | 一个慢 DNS 域名让 16 并发的整批 resolve 抛 TimeoutError，未捕获 → 本次采集整体失败（对 44 机场常态运行是致命路径）。建议 per-future timeout + 失败节点补空列表 |
| R-11 | **rdap 假重试** | enrich.py:52-53 | `for attempt in range(2)` 体内 `except Exception: break`——重试循环是死代码，注释宣称的"429/503 退避重试"不存在；rescan.py 注释同样引用该假机制。实际限流全靠 ip-api 45req/min 兜底 + workers=12（rdap_many :135-155）必然触发限流 |
| R-12 | **RDAP 磁盘缓存并发写损坏** | enrich.py `_save_disk_cache`（每个新 IP 全量重写整个 JSON，O(n²)）；rdap_many 用 ThreadPoolExecutor(12) 并发调 rdap | 多线程同时写 `data/.cache/rdap_cache.json` 无锁 → JSON 损坏 → 下次加载炸；且缓存无 TTL 永不失效，RDAP 归属陈旧。实测缓存已 3.56MB，每次全量重写成本线性恶化 |
| R-13 | resolve 超时不封顶 | enrich.py `resolve`（内层 executor `fut.result(timeout=5)` 但 `with` 退出 `shutdown(wait=True)`） | getaddrinfo 卡死时墙钟仍会拖满；collect 30s 总超时（R-10）与之叠加放大 |
| R-7 | **快照存储不可靠** | store.py `save`（秒级时间戳文件名、同秒覆盖、非 tmp+rename、无锁）；daemon 线程超时后仍可写（R-15） | Ctrl+C/崩溃时产生截断 json；`cmd_export`/`report` 读最新快照无 try 保护（run.py:1008,978），一个坏文件炸一阶段 |
| R-19 | **0 节点快照污染 diff** | store.py:41-54 `diff_latest` 无健全性门槛 | 某机场抓取失败得 0 节点快照 → 下轮 diff 报"全部节点消失" → alert 噪声/误报；反之"该消失的没消失"也检测不到。建议 diff 前置门槛：cur.nodes==0 时只告警"采集失败"不产出"全部消失" |

## 5. 华为检测引擎评估（detect.py + signatures/huawei.yaml）

### 5.1 机制

- 五维度独立匹配，命中即 Finding（confidence: rdap/domain/string=high，cidr/asn=medium）：`check_rdap`（子串 in netname+owner）、`check_asn`（去 AS 前缀后数字串相等）、`check_cidr`（ip∈network）、`check_domain`（签名子串 in 域名）、`check_string`（文本子串）。
- `scan_ip_record`（detect.py:71-92）：rdap/asn 命中→high；**仅在 rdap/asn 未命中时才查 CIDR**（`if ip and not out:`）；domain 命中→high。
- `scan_nodes`（detect.py:99-110）：只查节点 server 域名 + 已解析 IP；**节点名与 raw（SNI/ws_path/host）不走检测**——`check_string`（软件 strings 维度，huawei.yaml:64-73）在主采集流程中没有任何调用点，维度 4 实际闲置。
- 主判据 rdap_name（huawei.yaml:14-18：HWCSNET/HUAWEI/HWCLOUDS/华为）设计合理——签名文件自述"大量华为云 IP 挂在电信 AS23724/联通 AS4808 下运营"，与数据吻合。

### 5.2 误报面

| 来源 | 位置 | 影响 |
|---|---|---|
| **asn 136958=联通广东** | huawei.yaml:25（签名自注"华为云部分IP走联通ASN"） | **纯联通 IP 一律判华为**，medium 级；该条把"华为云租用联通线路"泛化成了"联通=华为" |
| CIDR 段自认不精确 | huawei.yaml:29-46（18 段，:34/:43 注明 114.115/139.159 部分非华为长城宽带） | 兜底维度误报率有下限；好在 detect 先 rdap 后 cidr 的次序挡掉一部分（rdap 命中即跳过 cidr） |
| 裸子串域名 | huawei.yaml:55-58 `hwcloud`/`hwcdn`/`agconnect` | `myhwclouds-xxx.com`（华为云客户域）、任何含 `hwcdn`/`agconnect` 的第三方域都命中 high |
| recon/scan_account_index 全文域名正则 | collect.py:273-294（`[a-z0-9.\-]+\.[a-z]{2,}` 全文抽取） | 页面里提到华为云文档链接即产生 finding，airport 维度语义被稀释 |
| memsan ip_port/domain_port 全堆扫 | memsan.py:58-76 | DNS 缓存/遥测/证书里的 ip:port 全进快照，检测输入本身已被噪声污染（误报上游） |

### 5.3 漏报面

| 来源 | 位置 | 影响 |
|---|---|---|
| check_string 未接入主流程 | detect.py（scan_text 无调用者） | 客户端二进制/APK strings 的 HMS 集成证据不会出现在采集快照的 findings 里 |
| asn 字段解析靠 remarks 含 "AS" 子串 | enrich.py rdap 解析 | RDAP 路径下 asn 常为空 → check_asn 维度基本依赖 ip-api 回退（as 字段），而 ip-api 又是限流+明文（R-11/R-6b）→ ASN 维度输入质量差 |
| rdap 失败=归属缺失 | enrich.py（失败给 `("n/a", "n/a(...)", "", "")`） | rescan 虽补扫（rescan.py `_needs_rdap`），但补扫只跑 `all` 一轮；ip-api 限流下 44 机场一轮补不全 |
| 域名维度只查 server | detect.py:99-110 | CNAME/NS 链路只在 recon 命令里查（recon.py），常规 pull 的节点不会带 cname 上下文 → `cdnhwc*` 类 CDN 边缘命中依赖 recon 单独跑 |
| 中文环境 CNAME 空洞 | recon.py `_dig`（R-36） | 中文 Windows 上 recon 的域名维度系统性失真 |

### 5.4 引擎小结

覆盖设计（rdap 为主、cidr 兜底、strings 保守）方向正确，签名文件注释质量高；主要问题是：① asn 136958 应降为"仅当 rdap_name 同现才升级"的辅助位或直接移除；② 裸子串 hwcloud/hwcdn/agconnect 改正则锚定（`(^|\.)hwclouds?[-.]`、`(^|\.)agconnect`）；③ scan_text 接入节点 raw 富集（SNI/ws_path/http host）；④ cidr 命中建议同时给 owner 复核提示（当前 medium 已是 medium，但 finding 文案没有"该段含非华为"提示）；⑤ 建立 fixtures 回归（把 scan_csv 的 CSV 当金标准集跑 CI）。
