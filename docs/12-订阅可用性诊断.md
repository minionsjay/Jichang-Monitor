## 2. 判定口径（四类定义 + 三个必须避开的坑）

| 类 | 定义（本报告采用） | 判据 |
|---|---|---|
| **A 订阅可用** | 本轮抓到节点且快照新鲜 | `14:58:04Z ≤ ts < 15:40:30Z` 且该快照节点数 > 0（上限见坑 1） |
| **B 订阅失效** | 配了订阅链接但本轮拿不到节点 | 在 `last_run.failed` 内，且以订阅为主通路；记原始 `reason` |
| **C 仅客户端** | 没有可用订阅链接，靠客户端配置出数 | 无订阅链接/无面板，只有 `client.core_process`；本轮 0 节点 |
| **D 断流** | 面板与订阅都不通 | 订阅非 2xx **且** 面板登录失败/不可达（客户端若有也 0 节点） |

三个坑（本报告已全部规避，写在这里是为了让后来者别踩）：

1. **`rescan` 会给"没拉到数据"的机场造一份伪新快照——这是本轮最大的坑。** 15:40:39Z–15:40:48Z（`run.py all` 收尾，总时长 2572 s）之间，采集器给 40 家各写了一份「最新态」快照。**其中 6 家本轮拉取失败的机场（bywave / kuainiao / xm999 / ss-id / oixcloud / qiangda）也拿到了 `ts=2026-10-21` 的快照，节点数却是 10-19 的旧值（20 / 61 / 77 / 15 / 47 / 86）**——只看"最新快照是否新鲜"就会把这 6 家判成健康。本报告的成功证据改为**硬条件**：`14:58:04Z ≤ ts < 15:40:30Z` 且该快照节点数 > 0；上限 15:40:30Z 由"伪新快照最早 ts = 15:40:39Z"倒推。
2. **`no-new-snapshot` ≠ 订阅坏了。** `pull_fail 11` 里 11 家 `reason` 全是 `no-new-snapshot`（抢占式采集器没产出新快照），它只说明"这一轮没拿到货"，具体是 401/403/超时/0 节点得回看 run 日志与快照内容——本报告 B/D 的区分正是靠这一步，不是靠 `reason` 字段。
3. **`nodes_total 1894` 不是节点总数。** 它把 40 家收尾重写的快照也算了进去，还夹着 0 节点快照（历史上这类空快照有 1135 份、横跨 16 家）。**按"每家取本轮最后一个有效快照"去重后为 1790 个节点。**

## 6. 对后续常态化监控的 5 条直接结论

1. **`nodes_total` 会骗人，`stale_over_6h` 更会骗人。** 本轮 `stale_over_6h` 只报了 jsqpro 一家，而实际有 13 家本轮 0 产出。原因两半：①6 家订阅失效的机场拿到了 15:40:4x 的**伪新快照**（见 §2 坑 1）；②另 5 家的最新快照是 0 节点的"空扫描"——lingdian / dovex / letsvpn 在 15:18、yiyuan 13:09、muniu 15:07，距今都不到 6 h，压根不触发阈值。只有 jsqpro 因为停在 10-19 才被抓到。**健康度判定必须换成"本轮窗口内非 0 节点快照"这条硬条件**，光看最新快照 ts 或 mtime 一定会漏，且漏的正是最需要告警的那几家。
2. **0 节点快照不该覆盖好数据。** `walk_client_dir` 在客户端未运行时也会写 `source=f"win_client:…"` 的空快照（本轮 fastlink 15:18、hhy 15:18、lingdian / dovex / letsvpn 15:18 都发生了），把"最后一次有数据"的时间戳往前推。建议：**节点数 0 的快照只写日志、不写 `data/<slug>/`**，或写入后保留上一份的 `last_ok` 字段供告警读取。
3. **伪新快照必须打标。** 40 份收尾快照里只有 7 份带 `(rescan)` 后缀，其余 33 份的 `source` 字段仍是原始订阅 URL——**与真实拉取完全无法区分**。建议加 `derived: true` + `origin_ts` 字段，或干脆不落盘（只供面板即时展示）。
4. **套餐到期是 D 类的最强前置信号（6 家里 5 家已过期/耗尽）。** `data/quota.json` 已有 `days_left`，应加规则：`days_left < 7` 或 `< 0` 直接进告警，不必等到订阅 401/403。这比事后诊断便宜一个数量级。
5. **B/C/D 必须在 UI 上分开。** 现在 `pull_fail 11` 把"机场故障（xm999 522）"、"我们的采集缺口（muniu-ninja）"、"客户端没启动（letsvpn）"混成一个数。三类责任人不同：机场侧=等，链接侧=我们改，客户端侧=把进程拉起来。建议 `sub_health.json` 的 `state` 直接进面板与日报。
