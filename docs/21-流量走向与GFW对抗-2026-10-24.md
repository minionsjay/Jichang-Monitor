# 流量怎么绕过 GFW：一次访问 google.com 的完整链路

> 2026-10-24 整理。参数全部来自本机 `data/` 里真实节点快照（不是教科书示例），
> 入口/出口对照来自 `.tmp_ver/exit_probe/` 的实测结果（见 docs/20）。

---

## 一、一句话原理

GFW 只能检查「你的电脑 ↔ 机场入口」这一段。机场要做的只有一件事：
**让这一段看起来像一次普通的、访问无害大网站的 HTTPS 访问**，
把真正的目标藏在加密隧道里，再由墙外的落地服务器替你访问。

---

## 二、完整链路（以 mojie「日本-优化」为例）

真实参数：

| 项 | 值 |
|---|---|
| 协议 | `vmess` + `network: ws`（WebSocket） |
| 入口域名 | `p6-olduser.linuxlh.xin:16617` |
| 入口 IP | `20.89.58.247` / `40.74.68.216`（Azure 日本） |
| 实测出口 | `66.90.99.58`（东京） |

```
【0】浏览器输入 google.com
      ↓
【1】本地客户端判定「走代理」，并且**不在本地解析 google.com**
      │   ★ 本地不发 DNS 查询 → 绕开 DNS 污染
      ↓
【2】客户端取出入口 20.89.58.247:16617
      │   ★ 你连的是 Azure 的 IP，不是 google 的 IP
      ↓
【3】TCP 三次握手 → Azure 日本
      │   ★ GFW 看到：又一个连 Azure 的普通连接（封段误伤企业客户太多）
      ↓
【4】TLS 握手
      │    ClientHello 的 SNI = 自有域名（或伪装成大站，见第四节 REALITY）
      │   ★ GFW 看到：一次正常的 HTTPS 访问
      ↓
【5】TLS 隧道内部：WebSocket → vmess 加密载荷
      │   载荷内容是「请帮我访问 google.com」
      │   ★ 这层加密，GFW 打不开
      ↓
【6】Azure 入口收包、解密，得到真实目标 google.com
      ↓
【7】入口 → 专线/中转 → 落地 66.90.99.58（东京）
      │   ★ 这一段在墙外，GFW 完全看不见
      ↓
【8】落地机以普通 HTTPS 访问 google.com
      │   ★ google 看到的源 IP 是 66.90.99.58，不是你的
      ↓
【9】google 响应 → 落地 → 隧道 → Azure 入口 → 你
      │   逐层解包：TLS → WebSocket → vmess → HTTP
      ↓
【10】浏览器渲染
```

**为什么第 2~5 步是整个方案的心脏**：这一段是唯一被审查的部分，
它必须同时满足「看起来无害」+「GFW 看不见内容」两个条件。

## 三、GFW 的手段 vs 机场的对抗

| GFW 的手段 | 机场怎么破 | 我们库里的证据 |
|---|---|---|
| **DNS 污染**：解析 google.com 返回假 IP | 本地不解析，域名塞进隧道让远端解析 | 节点 `server` 全是域名，`_resolved_ips` 由客户端在隧道内解析 |
| **SNI 明文检测**：握手时看到 `google.com` 就断 | 外层 SNI 写自有域名，或伪装成大站 | `servername: www.apple.com`（REALITY） |
| **IP 封锁**：封已知代理机房 | 入口放在 Azure/AWS/腾讯云，封段误伤太广 | 入口样本：Azure、AWS、腾讯云、Google、Microsoft |
| **协议指纹**：识别 VMess/SS 字节特征 | 套进 TLS + WebSocket，字节流等同普通 HTTPS | `network: ws`、`tls: true` |
| **流量特征**：包长、时序、上下行比 | 填充、多路复用、模仿网页浏览节奏 | 客户端开启 mux / padding |
| **主动探测**：主动连端口看应答像不像代理 | REALITY：探测者拿到真网站证书，验不出来 | 4 台腾讯云入口证书 SHA256 前 16 位全相同 `cd563f5716c254cc` |

## 四、REALITY：目前最彻底的伪装

我们库里有一条典型样本（bygcloud `xinaleye.owolist.cn`）：

```
vless + flow: xtls-rprx-vision + servername: www.apple.com
```

含义：客户端握手时 **SNI 直接写 `www.apple.com`**。

- 审查者看到的是「这个人在访问苹果官网」
- 服务端借用目标站的真实证书体系完成握手，**主动探测也验不出它是代理**，
  因为拿回来的确实是真苹果证书
- 代价：这条链路强依赖目标站的 TLS 特性，目标站被墙则整条不可用

> 注意区分：4 台入口证书指纹相同**不能证明**它们跑的是同一份部署，
> 只是「都伪装成同一个目标」的必然结果。

## 五、回程

原路反向，但两点值得注意：

1. **回程同样加密**，GFW 无法从下行数据反推内容，只有流量形状可用
   （「下行大、上行小」和看视频没有区别）。
2. **延迟构成**：`你↔入口` + `入口↔出口` + `出口↔google` 往返。
   这解释了为什么同一机场里，出口离入口越远越慢（见第七节实测）。

## 七、绕路代价：同一入口、不同出口的延迟差

对照组：cherryvpn 5 条 IEPL 节点，**入口全是 `13.230.160.161`（AWS 东京）**，
落地分别在日本 / 台湾 / 美国。因此延迟差 = 纯粹的「入口→出口」绕路成本。

测量方法：
- **入口 RTT**：Windows 侧 `socket.connect(入口IP, 端口)` 3 次取最小/中位
- **端到端 delay**：mihomo `/proxies/probe/delay` 打 `gstatic/generate_204`，3 次取中位
- **出口身份**：经同一代理请求 `ip-api.com`

实测（2026-10-24 深夜，各 5 次采样取中位；脚本 `.tmp_ver/latency_probe2.py`，原始数据 `.tmp_ver/exit_probe/latency2.json`）：

| 节点 | 入口 | 入口 TCP RTT（min / 中位） | 出口 | 端到端 delay（中位 / 最小） | 相对日本落地 |
|---|---|---|---|---|---|
| 日本08 | 13.230.160.161 | 78.5 / 85.6 ms | 东京 · Linode | **215 / 197 ms** | — |
| 日本07 | 同上 | 96.0 / 103.1 ms | 东京 · Linode | **165 / 162 ms** | — |
| 日本06 | 同上 | 99.9 / 101.0 ms | 东京 · Linode | **204 / 200 ms** | — |
| 台湾04 | 同上 | 86.0 / 94.5 ms | 台湾彰化 · 中华电信 | **350 / 253 ms** | **+150 ms** |
| 美国01 | 同上 | 95.6 / 96.5 ms | 美国俄勒冈 · AWS EC2 | **405 / 383 ms** | **+200 ms** |

三个观察：

1. **入口 RTT 几乎是常数**（78–100 ms）。同一台 AWS 东京、同样跨境专线，
   差异来自链路抖动而不是距离 —— 说明「你↔入口」这段对所有节点是一样的。
2. **出口每远一程，端到端多 150–200 ms**：东京→台北 +150 ms，东京→俄勒冈 +200 ms。
   这就是「专线说台湾、实际多绕一跳」的代价。
3. **同出口不同端口也能差 50 ms**（日本07 165 ms vs 日本08 215 ms，出口是同一个
   IP `172.104.74.37`）。说明延迟不只由地理决定，端口背后的入口机与线路负载同样关键。

> 采样注意：每个节点的**第一次**测量都异常高（791–1510 ms），那是 TLS 冷启动，
> 所以取 5 次的中位数而不是首次值 —— 否则会得出完全错误的结论。

## 八、这套方案的破绽（实测撞到的）

| 环节 | 会怎么坏 | 我们的实测证据 |
|---|---|---|
| 第 2 步：入口可达性 | 入口 IP 被墙 / 解析不到 | 多线池：同一域名 8~9 个 IP；机场频繁换域名 |
| 第 3 步：TCP | 能连上但应用层拒绝 | bygcloud 4 个百度 IP：TCP 通，TLS 立刻 `WinError 10054` |
| 第 4 步：TLS | 伪装目标被墙 / 证书校验失败 | REALITY 依赖目标站可用性 |
| 第 7 步：落地 | 落地被墙 / 线路拥塞 | 出口 IP 与入口不同，落地质量决定体验 |
| 入口本身 | 被识别后整条失效 | 机场最大的软肋，必须持续换入口 |

**结论**：不是「部署了多份」，而是「多个门 + 同一栋楼」。
入口是门，落地是楼，门可以被封，楼通常封不掉。

## 九、怎么自己验证

```bash
# 1) 查入口 IP（订阅里 server 是域名时）
wsl -d Ubuntu-22.04 -- dig +short @223.5.5.5 <入口域名> A

# 2) 查出口 IP：把节点导入客户端、选中它，然后
curl -s http://ip-api.com/json/        # 返回的 query 就是出口

# 3) 一键对比本机四路 DNS 与面板记录
python -X utf8 tools/dns_check.py <入口域名> --rdap
```

判断：
- 返回的出口 IP **等于**入口 IP → 直连型（入口即出口）
- 返回的出口 IP **不等于**入口 IP → 中转型，那个新 IP 才是真正的落地

## 十、一句话总结

> 机场卖的不是「一个 IP」，而是「一段替你被审查的路径」：
> 入口负责骗过审查，隧道负责藏住目标，出口负责替你出网。
> 三者由不同机器承担，任何一段坏掉，链路就断。
