## 1. 信息架构（六大区块）

```
┌──────────────────────────────────────────────────────────────────┐
│ ① KPI 总览条   机场数(有节点/总数) · 节点总数 · 华为命中 · 零节点/陈旧名单 · 数据基准时间 │
├──────────────────────────────────────────────────────────────────┤
│ ② 44 机场状态卡片矩阵（搜索框 + 状态筛选 + 排序；点卡片展开详情）              │
│    卡片=机场名/节点数/Δ(±N)/路线/协议分布/最近快照时间+陈旧度/状态徽标          │
│    详情=节点表(名称/协议/server:port/国家) + 增删清单 + 命中 + 落地厂商Top + 到期  │
├──────────────────────────────────────────────────────────────────┤
│ ③ 最近两次快照 diff（新增/消失节点，按 |Δ| 降序，逐机场可展开）               │
├──────────────────────────────────────────────────────────────────┤
│ ④ 告警流（alerts.log 有效块倒序；空块过滤；华为命中高亮 + churn 计数）         │
├──────────────────────────────────────────────────────────────────┤
│ ⑤ 华为命中区（当前快照 findings + alerts.log 历史去重台账）                  │
├──────────────────────────────────────────────────────────────────┤
│ ⑥ 运行健康区（每机场最近成功时间/路线/0节点/陈旧度 + run.log 最近完成一轮解析）   │
└──────────────────────────────────────────────────────────────────┘
```

### ① KPI 总览条
- 有节点机场数 / 快照目录总数、节点总数、华为命中条数（当前快照口径）。
- 异常名单：**本轮 0 节点**机场、**陈旧**（>6h 无新快照，阈值可配）机场——直接呼应 t3 的"yiyuan 断档无监控手段"盲区。
- 数据基准时间 = 全部机场最新快照的最大时间（保证同一份 HTML 内陈旧度口径自洽）。

### ② 机场状态卡片矩阵
- 一卡一机场，默认按节点数降序；支持按名称搜索、按状态（正常/0节点/陈旧/有命中）筛选、按节点数/Δ/陈旧度排序。
- 卡片元素：机场名、节点数（大字）、相对上一份非空快照的 `+新增/−消失` 计数、采集路线徽标（sub-url / server-fetch / v2board / velo-api / xlcc / memory-scan / manual）、协议 Top3、最近快照本地时间 + "x 小时前"、状态徽标。
- 点击卡片 → 详情面板：节点明细表（节点别名、协议、`server:port`、落地国家）、新增/消失节点逐条清单、华为命中、落地厂商 Top5（RDAP owner）、账号到期/用量（订阅头部有该信息时）。

### ③ 最近两次快照 diff（新增/消失节点）——"看见变化"的核心区块
- 全部机场按 `|新增|+|消失|` 降序排表；行内 `<details>` 展开逐条节点（`名称 — 协议 server:port (国家)`）。
- **双口径规则（关键设计决策）**：
  - `diff` 在**最近两份非空快照**（nodes>0）之间计算，而不是"最新两份文件"。
  - 理由（t3 §4.4/§5.2 + 实证）：同一轮内 1/5 拉取会先落一份快照，2/5 客户端扫描与 3/5 rescan 再落/重写；muniu/wdy 的拉取路线**恒 0 节点**（真实数据来自客户端兜底），若按"最新两份文件"diff，会把"拉取 0 节点"当成"整池消失"，正是 t3 R-19 指出的 0 节点污染 + 同轮自差问题。
  - 最新文件若为 0 节点，不隐藏：卡片与健康区显式标"本轮拉取 0 节点"徽标（真实异常仍可见，如 yiyuan 断档、jsqpro 间歇）。

### ④ 告警流
- 解析 `data\alerts.log` 的 `===== TS | airport =====` 分块，**过滤 83.9% 的空块**（t3 §4.2 已定位根因：`store.diff_latest` 恒 truthy），仅保留有内容的块。
- 每块显示：时间（本地化）、机场、类型徽标（华为命中 / churn）、新增/消失计数、命中文原文。
- 默认倒序保留最近 120 个有效块（可配 `--alert-limit`）。
- 与 R1/R2 的关系：仪表盘是"过滤后的展示"，不修 alerts.log 本身；空块修复（R1）与分级推送（R2）属 04-优化方案。

### ⑤ 华为命中区
- **当前命中**：各机场最新（非空）快照的 `findings[]`（字段 `dimension/rule/evidence/context/confidence`），当前常态为 0（t1/t3 结论：服役华为 CDN=0）。
- **历史台账**：从 alerts.log 华为命中行按 `(机场, rule, evidence)` 去重，给"最近一次出现时间 + 累计次数"——t3 §4.3 的 13 块命中在页面上有一张永久的可查台账，不再靠手工翻日志。
- 每条显示：机场、维度=规则、证据、上下文（节点）、置信度。

### ⑥ 运行健康区
- **每机场行**：最近成功时间（最新快照 ts）、陈旧小时数、24h 快照数、采集路线、节点数、状态（正常/0节点/陈旧/无数据）。默认按陈旧度降序——一眼看出"谁最久没出数"。
- **run.log 最近一轮解析面板**（best-effort）：从 run.log 尾部（2MB）定位最近**有完成标记**的一轮，展示：开始/完成时刻与耗时（来自 `auto_run.bat` 写入的 `=== %date% %time% ===` / `Done %date% %time% ===` 锚行，ASCII 数字在混编码下可存活）、`[成功] slug (kind): N 节点` 汇总、`[跳过] 超时`名单、`⚠ 0 节点`名单（按"正在拉取 slug"上下文归属）、登录失败名单、final 汇总（X 机场 / Y 节点）。若尾部存在无完成标记的新一轮，标注"检测到进行中/被中断的一轮"。
- **失败原因的口径限制（如实声明）**：MVP 的"失败原因"= 本轮 run.log 的超时/0 节点/登录失败三类行 + 每机场 0 节点徽标。**完整的按机场失败归因**需要结构化运行摘要（t2 R-32 / t3 R11 的 `data/last_run.json` 建议）——那是仪表盘健康区的 V2 数据源，MVP 不从 21MB 混编码日志里做重型归因解析。

## 2. 数据来源映射（区块 → 文件 → 字段）

### 2.1 快照 JSON 结构（实证抽样结论）

```
data\<airport>\<YYYYMMDDTHHMMSSZ>.json
├─ airport: str                      # 机场 slug
├─ ts: "2026-10-16T12:28:39Z"        # ISO UTC
├─ source: str                       # ⚠ url 路线时含订阅 token —— 严禁进仪表盘
├─ nodes[]: { name, protocol, server, port, raw{...} }
│    └─ raw: { source, password⚠, sni/alpn/cipher/type...(协议相关),
│              _resolved_ips: [ip...], _rdap: {ip: [netname, maintainer, country, org]} }
├─ findings[]: { airport, dimension, rule, evidence, context, confidence }
└─ meta: { subscription-userinfo?, profile-update-interval?, panel_type?,
           processes?, app_signature⚠?... }   # 按路线不同
```

- 实证：cherryvpn（manual-url，anytls×122+hysteria2×1，meta 有 subscription-userinfo）；velochron（velo_api，aero_v2×33，raw 含 aero_v2_edge_psk/aead_key 等**敏感键**）；hhy（memory_scan，unknown×170，name=node-<port>）；ss-id（sub-url，ss×15）。
- 目录口径：`data\` 下 47 个机场目录 + 2 个逆向分析目录（`speedcat_analysis`、`wandacloud_analysis`，内含非快照命名 JSON）+ `.cache`。**只认文件名匹配 `^\d{8}T\d{6}Z\.json$` 的目录为机场**，自动排除分析目录与缓存。

### 2.2 映射表

| 区块 | 来源文件 | 使用的字段/行 | 加工逻辑 |
|---|---|---|---|
| KPI/卡片/详情 | `data\<a>\<ts>.json` | `nodes[].name/protocol/server/port`、`raw._resolved_ips`、`raw._rdap[ip][2]`(国家)、`findings[]`、`meta["subscription-userinfo"]`(expire/total/upload/download) | 白名单取字段；`_rdap[ip][0]/[1]` 聚合落地厂商 Top（同 `airmon\report.py:_owner` 的去尾巴逻辑）；协议 Counter；国家 Counter |
| 卡片路线徽标 | 同上 `source` | 仅取**前缀分类**：`memory_scan:`→memory-scan(显示客户端名)、`velo_api`→velo-api、`server-fetch`/`v2board`/`xlcc`→同名字段内关键词、`http(s)://`→sub-url(**不显示原文**) | 防订阅 token 泄漏的关键设计：source 只分类不透传 |
| ③ diff | 最近两份**非空**快照 | `nodes[]` 按 `protocol://server:port`（即 `Node.key()` / `store._key` 口径）求差集 | 复用 `airmon.store.list_snapshots/load`；差集元素白名单化（name/protocol/server/port/country） |
| ④ 告警流 | `data\alerts.log` | 块头 `===== TS \| airport =====`；行 `华为关联命中 N 条：`、`  [华为命中] ...`、`新增节点 X 个`、`消失节点 Y 个` | 分块→判空→倒序截断；与 `airmon\alert.py:emit` 的写格式一一对应 |
| ⑤ 华为历史台账 | `data\alerts.log` | `[华为命中] <airport> \| <dimension>=<rule> \| 证据=<evidence> \| <context> (<confidence>)` | 正则解析 + `(机场,rule,evidence)` 去重计数 |
| ⑤ 华为当前命中 | 最新非空快照 | `findings[]` 全字段 | 直出 |
| ⑥ 健康区（机场行） | `data\<a>\*.json` 文件名 | 文件名时间戳（UTC）→ 最近成功时间/陈旧度/24h 快照数 | 文件名即真相，不读文件体，47×~1300 个文件名扫描成本可忽略 |
| ⑥ 健康区（本轮面板） | `run.log` 尾部 2MB | bat 锚行 `=== %date% %time% ===` / `Done ... ===`（ASCII 可解析）；python 行 `[成功] (\S+) \(([^)]*)\): (\d+) 节点`、`[跳过] (\S+): 超时`、`⚠ 0 节点：`、`\[(\S+)\] ✗ 登录失败`、`===== 完成：(\d+) 个机场，共 (\d+) 个节点` | UTF-8 errors=replace 解码（GBK cmd 行乱码但 ASCII 锚点存活，实证通过）；取最近有完成标记的一轮 |
| 数据基准 | — | 全部机场最新快照 ts 的最大值 | 所有"x 小时前"以基准时间为原点，保证同一份 HTML 自洽 |

### 2.3 脱敏红线（实现层用"白名单字段"硬保证）

| 严禁出现在 index.html | 出处 | 处理 |
|---|---|---|
| 订阅 URL/token | 快照 `source`（http 路线）、`credentials.yaml` | source 只输出路线分类词；credentials 一律不读 |
| 节点密码/UUID | `raw.password`、memsan 密码字段 | 不取 raw 内除 `_resolved_ips/_rdap/source` 外的任何键 |
| Velochron 密钥 | `raw.aero_v2_edge_psk/aead_key/resume_ticket/...` | 同上，白名单外全丢弃 |
| 账号邮箱/cookie/auth_token | credentials.yaml、`raw.auth_id`、winclient meta | 不读不取 |
| `meta.app_signature/app_version` | velochron meta | 不取（防逆向指纹外漏，虽非凭据也按最小化处理） |

> 允许出现（任务书明确许可）：聚合统计、节点别名（name）、`server` 域名或 IP、端口、协议、国家/厂商（RDAP 四元组）、增删变化、时间戳。
> 遗留提醒：`dashboard\index.html` 与 `nodes_export.csv` 同级敏感（含全部落地基础设施），建议 04-优化方案把 `dashboard/` 加进 `.gitignore`（本任务无权改 .gitignore，未改）。

## 3. 技术选型对比：纯静态生成 vs 本地常驻服务

| 维度 | A. 纯静态单文件生成（**MVP 选它**） | B. 本地常驻服务（Flask/FastAPI + 前端） | C. 增强 report.md（纯文本） |
|---|---|---|---|
| 交互 | 生成时固化数据 + 页内 JS 搜索/筛选/展开 | 实时查询、任意钻取 | 几乎无 |
| 部署成本 | 0：无端口、无进程、无守护 | 常驻进程 + 端口管理 + 开机自启 + 崩溃重启 | 0 |
| 与现有调度契合 | 完美：挂在 `cmd_all` 尾部，每轮自动再生，与"3h 一轮"节奏天然同步 | 需要另一条常驻生命周期，与计划任务双轨（正是 t3 §7.2 G8 批评的形态） | 完美但表达力差 |
| 依赖 | 0 新依赖（标准库 json/glob/re + 现有 airmon） | +web 框架 + 前端构建链（或裸 JS 多文件） | 0 |
| 离线/隐私 | 数据不出盘、不监听、双击即开（file:// 可用，无 CDN 外链） | 本机端口暴露面 +1 | 不出盘 |
| 故障面 | 生成失败不影响主流程（接线处 try/except 隔离） | 服务挂了 = 看板全挂，多一个需要监控的组件 | 低 |
| 弱点 | 每轮整页重生成；数据是快照视图非实时；文件随数据量增大（当前 ~0.5MB 量级，可控） | MVP 阶段过度设计 | 无法承载卡片/筛选/展开交互 |

**结论**：44 机场单机 Windows + 计划任务 3h 一轮的形态下，用户要的是"每轮跑完打开看一眼"，静态单文件以零运维成本满足全部 MVP 需求；常驻服务属于"要远程看、要实时钻取、要多端看"的阶段（与 deploy\ 方案 B 同一成熟度门槛），留作 V2。选 C（只增强 report.md）无法承载"状态卡片 + 筛选 + diff 展开"的交互要求，仅作为兜底保留（report.md 继续生成，二者并存）。

## 4. MVP 实现说明

### 4.1 文件与用法

```
airmon\dashboard.py        # 生成器（唯一新代码文件）
dashboard\index.html       # 输出（自建目录）
```

```bash
python -m airmon.dashboard                 # 全量：44+ 机场 → dashboard\index.html
python -m airmon.dashboard --airport muniu # 单机场快跑（页面对应裁剪）
python -m airmon.dashboard --out D:\x.html --alert-limit 200 --stale-hours 6
```

### 4.2 模块结构（airmon\dashboard.py 内部）

| 函数 | 职责 |
|---|---|
| `iter_airport_dirs()` | 枚举 `data\` 下含快照命名 JSON 的目录（排除分析目录/.cache） |
| `_load_snap_n(snaps, n)` | 从第 n 新文件向前找第一份可解析快照（容错截断 JSON，t2 R-7 非原子写风险） |
| `collect_airport(slug)` | 单机场聚合：latest/best 双轨、diff（非空快照间）、协议/国家/厂商 Counter、findings、meta 到期解析、24h 快照数 |
| `parse_alerts(limit)` | alerts.log 分块→过滤空块→倒序 N 块 + 华为台账去重 |
| `parse_run_log(tail_bytes)` | run.log 尾部最近完成一轮解析（含 bat 时间锚、超时/0节点/登录失败名单、final） |
| `build_data(...)` | 组装嵌入 JSON（含 KPI、status 分类、基准时间） |
| `render_html(data)` | 单文件模板：内联 CSS/JS，JSON 以 `<script type="application/json" id="dashboard-data">` 注入（`</` 转义防破壳） |
| `generate(...)` | 编排 + 写文件 + 控制台摘要；`main()` 提供 argparse（`--airport/--out/--alert-limit/--stale-hours/--runlog-tail`） |

### 4.3 run.py 最小接线（唯一被修改的现有文件）

位置：`cmd_all` 5/5 段汇总打印之后（`run.py:994` 之后、`cmd_export` 之前），恰好在"完成：X 机场 Y 节点"打出后执行：

```python
    # 6/5 仪表盘（best-effort，失败不影响主流程与退出码）
    try:
        from airmon.dashboard import generate
        print(f"仪表盘 → {generate()}")
    except Exception as _e:
        print(f"[仪表盘生成失败，忽略] {_e}")
```

- 5 行、try/except 全包、异常只打印不上抛——不会改变 `cmd_all` 的任何失败语义（t2 R-17 指出退出码恒 0 的问题保持原样，不由本次接线引入新行为）。
- 在流水线末尾执行的时序收益：3/5 rescan 与 4/5 export 已完成，快照集处于轮内最终态，仪表盘与 CSV/报告读到同一份世界。

### 4.4 性能与体量预算

| 项 | 估算 | 控制 |
|---|---|---|
| 快照读取 | 每机场 2–3 份 JSON（≤3 份 × ~50KB × 47） | 只读 needed 文件，不全量扫 2.2GB |
| 文件名扫描 | ~44,000 个文件名排序 | 只为 24h 计数与最新序，无文件体 IO |
| alerts.log | 751KB 全读一次 | 分块后只留尾部 N=120 有效块 |
| run.log | 尾部 2MB | 可 `--runlog-tail` 调 |
| 嵌入 JSON | ~2700 节点白名单字段 + diff 清单（单侧截断 200 条/机场，保精确计数）+ 120 告警块 | 实测目标 <1.5MB，典型 ~0.5MB |
| 浏览器渲染 | 47 卡片 + 6 表格，纯 vanilla JS | 无框架无外链，file:// 直开 |
