# 07 · 通过流量/网流特征识别机场节点的可行性验证

- 日期：2026-10-18
- 作者：traffic-researcher（AI 辅助研究）
- 数据基线：`data/` 下 47 家机场、约 4.4 万份快照 JSON（2026-07-28 起）、`data/alerts.log` 全期、`data/nodes_export.csv`（2,524 行）、`signatures/huawei.yaml` 五维签名
- 方法：本地抽样画像脚本（存 %TEMP%，未进 `data/`；抽样策略 = 每机场最新 4 份 + 最早 1 份快照，共 13,452 节点条目）+ 全量 `nodes_export.csv` 交叉校验 + 参考文献调研（4 篇内部调研文档 + 公开论文/厂商资料）
- 机密声明：本文零机密。不含 password / token / sub_url / 完整订阅地址；所有 IP 仅保留前 3 段（末字节以 `x` 掩码）；域名仅保留 TLD 统计与公共基础设施域名。

## 0. 摘要（TL;DR）

1. **「华为云签名」路线在节点侧被证伪**：47 家机场、1.3 万抽样节点 + 2,524 行全量导出中，节点 server/落地 IP 命中 `huawei.yaml` 五维签名的数量为 **0**。alerts.log 里的 13 行华为命中全部来自**面板/注册侧 IP**（如 Huawei-Cloud-Hongkong 的 119.8.242.x），与节点转发基建无关。机场真正的高频驻留地是 **AWS（约 30%）、腾讯云、百度智能云（单 org 最高 1,748 条）、中华电信、Oracle、GCP**。
2. **区分度最高的离线指纹不是「云是谁」，而是「一 IP 挂几百个端口、几十上百个节点」**：单 IP 复用系数极端化（ayucloud 669 节点/2 IP、applegame 149/1、lingdian 854/33），叠加 67–69% 节点使用 10k–65k 高位端口——这是普通网站/CDN **不会出现**的拓扑形态，是可量化的好指纹。
3. **第二梯队指纹**：RDAP 机构在机场内部高度集中（每机场 1–3 家机构覆盖 >80% 节点）、跨机场共享少数 maintainer（netutils-mnt 一家跨 9 个机场）；域名侧的廉价 TLD 集中（.xyz/.cc/.top/.sbs）、伪 TLD（`.go`、`.internal`）、随机短子域；以及占位假节点（公共 DNS IP、`pprof.go` 一类残留）和极高 churn（42 机场新旧快照节点集 Jaccard 中位仅 0.582，5 家机场完全换血）。
4. **离线（不抓包）能走多远**：凭现有快照即可构建「机场基建画像库」，对「某 server/IP 是否机场节点资产」做多特征联合判定，预期准确率足以支撑监控仪表盘；但它只能回答「是不是机场的资产」，**不能回答「此刻该 IP 上是否真的在跑代理转发」**——后者必须流量观测或主动探测，主动探测因合规风险明确不做。
5. **MVP 建议**：分三阶段。Phase A（纯离线，2–3 人日）：把 `huawei.yaml` 单一签名升级为「IDC/云厂商 + RDAP org + 单 IP 扇出」画像库，接入现有 alerts 管道与仪表盘；Phase B（3–5 人日）：DNS 被动观测（本地递归日志记录节点域名解析漂移）；Phase C（5–10 人日）：家用路由 NetFlow 导出验证 F1/F3/F5 三个会话级特征。总量约 3 人周。

## 1. 本地数据画像（47 机场实测）

### 1.0 方法与口径

- 抽样：每机场取**最新 4 份 + 最早 1 份**快照（跨时间对比用），共 13,452 节点条目；解析 1.99 万人次（`_resolved_ips` 展开后逐条计）。全量校验用 `data/nodes_export.csv`（2,524 行、44 机场，为某次全量导出）。
- 字段来源：`name/protocol/server/port` 取节点顶层；`_rdap` 取 `raw._rdap[ip]` 四元组（netname/org/country/ASN 串）。
- 12 家机场（dovex/fastlink/hhy/letsvpn/lingdian/qingyunti/quqiuquan/speedcat/ssrdog/wandacloud/wdy 等）来自 memory_scan 来源，`protocol=unknown`、节点名 `node-443/node-666` 风格——它们计入形态统计但排除出「协议多样性」结论。
- 区分度评级标准：★☆☆ = 无区分度或反指标；★★☆ = 弱；★★★ = 中；★★★★ = 强（普通网站/CDN 集中不会出现、机场集中出现）。

### 1.1 server 形态：83% 域名、17% 裸 IP，但 IP 直连型机场呈双峰分布

- 全量（nodes_export.csv）：domain 2,091（83%）vs IP 433（17%）。
- 但按机场分层后是**双峰**：letsvpn 95%、yiyuan 98%、neko77 94%、ssrdog 74%、wandacloud 75%、qingyunti 56%、hhy 50% 以裸 IP 作 server；其余机场几乎全域名。
- 区分度：★★☆。裸 IP 高位端口 + 无 SNI 场景与正常网站运维差异明显，但「用域名」才是机场主流，此特征只能给 IP 直连型机场加分。

### 1.2 端口分布：67–69% 落在 10k–65k 高位区，且机场内部高度集中

抽样 13,452 条：10k–65k 9,023（67.1%）、443 1,729（12.9%）、1k–10k 2,106、<1k 470、CF 备用口 33、80 12。
全量 2,524 行：10k–65k 1,749（69.3%）、443 357、1k–10k 309、<1k 98。

Top 端口：443、20443、8443、10040、1980、60000、5402、30001、25456、44553、8080，及连续段 28202–28207（各 43 条，典型的批量生成段）。同一机场的节点端口常挤在同一万位段（如 28xxx、39xxx）。

- 调研注记：2052/2053/2082-2096 是 **Cloudflare 备用端口**，非 V2Ray 专用，不能单独当指纹（详见 §3.4 误用清单）。
- 区分度：★★★。普通网站集中在 80/443，CDN 回源也极少用 10k–65k；机场近 7 成在高位区且**同机场批量占用连续段**。注意 CDN 中转型机场（走 443+CF）会让此特征漏报，因此不能单独定性。

### 1.3 单 IP 扇出（复用系数）：全场最强指纹 ★★★★

每机场「节点数 / 唯一落地 IP 数」：

| 机场 | 节点数/IP 数 | 系数 | | 机场 | 节点数/IP 数 | 系数 |
|---|---|---|---|---|---|---|
| ayucloud | 669/2 | 334 | | bygcloud | 519/16 | 32 |
| applegame | 149/1 | 149 | | wandacloud | 596/14 | 43 |
| ssrdog | 222/2 | 111 | | kuainiao | 329/17 | 19 |
| cherryvpn | 620/7 | 89 | | hhy | 790/17 | 46 |
| maxiong | 553/8 | 69 | | lingdian | 854/33 | 26 |
| ss-id | 75/1 | 75 | | qiangda | 405/14 | 29 |

（另一半机场靠域名轮换，扇出体现在 DNS 侧，见 §1.5/§2。）

对照基准：一个普通网站 = 1 个服务 IP 承载 80/443 两个端口、1 个证书；CDN 边缘节点 = 1 IP 承载海量**不同客户域名**但同是 80/443。机场的形态是 **1 个 IP × 几十到几百个不同高位端口 ×（常为）同一证书策略**。这是端口维度（§1.2）与拓扑维度合并后的复合特征，普通互联网流量没有对应物。

- 区分度：★★★★。即使用户侧只看得到「连向同一 IP 的多个不同目的端口的长连接」，也足以触发怀疑。

### 1.4 RDAP/ASN：机构集中 + 跨机场共享，华为云零命中（假设证伪）

**分类占比**（1.99 万条解析，每条解析计）：other/未识别 8,177（41%）、AWS 5,881、腾讯云 2,573、中国运营商 696、微软 646、阿里云 454、Google 436、Cloudflare 407、Megaport IDC 156、Oracle 149、Vultr/Choopa 81、PCCW-HKT 71、Meta 69、GWBN 60、Linode/Akamai 37、DigitalOcean 15。**大云合计约 50.9%**。华为云 = **0**。

**Top 机构名**（占 35.8% 仅 5 家）：Baidu Noc 1,748（bygcloud 一家占 1,664）、AWS EC2 ap-ne-1 1,520、James Tian 1,505（bygcloud 1,454，个人 maintainer）、AWS EC2 ap-se-1 1,272、Amazon DS SG 1,075。次级：netutils-mnt 975（**跨 9 个机场共享！**）、ACEVILLE PTELTD 938（hhy 754）、HINET 768（ayucloud 669 全在中华电信）、Tencent Cloud 686、DoD NIC 672（letsvpn 670，美国防部网段被廉价转售）、Microsoft 608（cherryvpn 492）、Google 420、China Mobile 292。

三个可直接落库的结论：

1. **机场内部集中**：每机场 1–3 家 RDAP 机构覆盖 >80% 节点。「一个域名体系下 90% 流量去往同两家 IDC」是强信号。
2. **跨机场共享 maintainer**：netutils-mnt、ACEVILLE、HINET、DoD NIC 等出现在多家机场——RDAP org/ASN 维度天然构成「机场基建图谱」的连接边，单看一家机场看不到。
3. **`huawei.yaml` 对节点侧完全失效**：五维签名（RDAP 名/域名/ASN/CIDR/字符串）在全部抽样与全量导出中华为命中 0。alerts.log 仅有的 13 行华为命中（quqiuquan 5、speedcat 4、muniu 2、muniu-ninja 1、chaoyue 1）证据均为 Huawei-Cloud-Hongkong / regip=119.8.242.x——即**注册与面板侧**用了华为云国际版，而非节点转发侧。与调研文档一致：华为云大量 IP 挂在非华为 ASN（电信/联通）下，rdap_name 才是主判据——但即便按 rdap_name 放宽，本数据集节点侧仍为零。
- 区分度：RDAP 机构集中度 ★★★★；「是否特定云厂商」★☆☆（要跟/org 而不是跟「云」这个概念）。

### 1.5 域名形态：廉价 TLD、伪 TLD、随机子域、DNS 轮换 ★★★★

TLD 分布（抽样）：com 4,305、xyz 1,889、cc 713、us 669（全部 ayucloud）、cn 519（全部 bygcloud）、space 350（hhy）、org 325、net 285、**internal 217（dovex 伪 TLD）**、online 207、top 190、club 97、**go 94（非真实 TLD，`pprof.go` 类残留节点）**、sbs 71、pub 49……单机场 TLD 高度集中（一家机场基本 1–2 个 TLD 打天下）。

- 廉价/异常 TLD（xyz/cc/space/online/top/club/sbs/cyou/xin/shop/pro/pub + 伪 TLD）合计占比约 19%；`.us/.cn/.space` 这类「一家机场独占一个 TLD」的绑定关系本身就是可入库指纹。
- 子域形态：节点 server 子域普遍是「短随机串 + 地域词」（如 `scapp-pk6f8zb.llguanglisf.com`、`39145.linknode.cc`——前缀即端口号），配合 §1.8 的 churn，说明**域名高频批量生成**。普通企业域名几乎从不开 `.xyz` 挂 4 段随机子域。
- 区分度：★★★★（TLD 绑定 + 随机子域 + 高 churn 联合判定）。

### 1.6 节点命名模式：可用但弱 ★★☆

地域词 85.6%、含数字 84.6%、emoji 34.5%、IEPL/IPLC/专线词 7.3%、流媒体/AI 解锁词 4.7%、家宽/原生 2.1%、中转 1.7%、协议词 1.2%、入口/出口 0.2%；`cdnhwc*` = **0**（华为命名假设同样证伪）。

- 「香港 01 ×2」「🇭🇰 IEPL-03」式命名与商业 CDN/官网毫无交集，但它是机场**自己标注**的信息，机场可随时改名，属弱指纹。
- 真正有价值的是命名里的**功能词**：IEPL/专线/中转词直接暴露「该节点是转发链中继」——对 §2 的链路建模有用。
- 区分度：★★☆（辅助字段，非独立判据）。

### 1.7 占位/假节点与订阅噪音 ★★★（可用作负样本清洗）

跨机场共享 IP 仅 63/1,387，且几乎全是公共解析与占位：1.12.12.12（8 机场，DNSPod DoH）、120.53.53.53（7）、8.8.8.8（5）、17.253.x（Apple，5）、104.16.x（Cloudflare，5）、223.5.5.5/223.6.6.6（3）、239.255.255.250（SSDP，3）。域名侧同理：`pprof.go`（8 机场！）、doh.pub（7）、cloudflare.com（6）、gstatic.com（5）、apple.com（5）。

- 结论：**订阅流里混着官网域名、DoH、测试假节点**；`pprof.go` 这种伪 TLD 能跨 8 家机场出现，说明多家机场共用同一套订阅生成器/模板。画像库必须先做「占位节点过滤」，否则假节点会污染一切统计。
- 区分度：★★★（作为负样本规则价值大于正向指纹）。

### 1.8 生命周期与 churn ★★★

- alerts.log 全期：新增节点 68,473 / 消失 27,963。大户：maxiong +42,414、yiyuan +9,728、wdy +8,289、feiniao +2,445、chaoyue +1,271。
- 42 机场「最老 vs 最新」快照节点名集合 Jaccard：中位 0.582、最小 0.0（ayucloud/dualnet/flybar/velochron/wandacloud 完全换血）、最大 1.0。
- 解读：机场节点以「天」为单位批量更换子域/端口，但**落地 IP 与 RDAP 机构相对稳定**（否则画像库失效）。这正是「IP/ASN 稳定、域名端口轮换」的第二层指纹：一个基建上跑着不断改名的节点流。
- 区分度：★★★（需时间序列快照，现有数据已支持）。

### 1.9 协议分布与单机场同质性 ★★☆

抽样协议：unknown 5,233（38.9%，即 memory_scan 来源）、anytls 2,304、vless 1,894、ss 1,470、hysteria2 862、mieru 514、vmess 420、trojan 249、ninja 175、aero_v2 132、hysteria 128、tuic 11。异类协议 mieru/ninja/aero_v2 在场，说明尾部机场已转向抗检测协议。

单机场协议同质：applegame 全 trojan、ayucloud 全 ss、bygcloud 全 vless、oixcloud 全 anytls、neko77 mieru、velochron aero_v2、muniu-ninja 全 ninja。协议异质度可作为「订阅结构正常性」指标，但对流量识别帮助有限——协议字段是订阅自述，可造假，且观测者（网流层）根本看不到它。

## 2. 特征分层：离线可提取 vs 需流量观测

### 2.1 离线可提取（现有快照数据即可算，零新增部署）

| 特征 | 计算来源 | 本数据集验证结果 |
|---|---|---|
| server 形态、端口分布、扇出系数 | 快照 `server/port/_resolved_ips` | §1.1–1.3 |
| RDAP org/ASN/CIDR 画像库 | `raw._rdap`（已有 rdap_cache 机制） | §1.4 |
| TLD/伪 TLD/子域熵 | 快照 `server` | §1.5 |
| 命名功能词 | 快照 `name` | §1.6 |
| 占位节点过滤 | `server` ∪ `_resolved_ips` ∩ 公共 DNS/CDN 白名单 | §1.7 |
| churn/换血率 | 跨快照对比（已有 alerts.log 管道） | §1.8 |
| 跨机场基建图谱 | org/ASN/CIDR 反查 | §1.4 |
| 证书/SNI 逻辑一致性 | `sni` vs `server` vs `skip-cert-verify` | 抽样可见大量 skip-cert-verify=true，弱信号 |

离线层的天花板：**只能证明「资产属于机场基建」，不能证明「该资产此刻在跑代理」**。域名可以指到云上闲置机器，IP 可以转售，画像会滞后于机场换基建。

### 2.2 需流量观测（要抓包/NetFlow/长连接统计/时序）

以下特征全部无法从订阅快照获得，必须观测真实流量。观测对象是**自家设备访问自家订阅节点**的流量：

| 特征 | 观测什么 | 为什么离线拿不到 |
|---|---|---|
| F1 单端口海量会话 | 同一目的 IP:port 上并发/累计会话数 | 快照只有「配置了哪些节点」，无使用强度 |
| F2 会话源极分散（服务端视角） | 需在服务端看——用户侧不可得 | 仅云厂商/机房侧可观测 |
| F3 方向字节不对称（>5 或 <0.2） | 上/下行字节数比 | 需流量计数；代理转发下行远大于上行 |
| F4 平均包长分布 | 包级统计 | 需抓包或带包数计量的 NetFlow |
| F5 超长连接占比 | 连接持续时长分布 | 需流记录；代理长连接（视频/下载挂机）远超网页 |
| F6 单一目的端口承接 >90% 连接 | 端口会话集中度 | 同 F1 |
| F7 目的 IP 极少数化（个位数境外 IP 承接全部流量） | 目的 IP 基数 | 用户侧同样可得！只需 NetFlow 五元组 |
| F8 20:00–24:00 晚高峰突发 | 时序 | 需时序流记录 |
| TLS 指纹 JA3/JA4 | ClientHello 参数 | 需抓 TLS 握手明文头（SNI 之外的扩展/密码套件序） |
| TLS-in-TLS 嵌套检测 | 内层握手包长/时序模式 | 需 DPI 级观测（USENIX Sec'24 方法） |
| 包长时序/站点指纹 | 前 N 包载荷长度序列 | 需完整抓包 + ML 模型 |
| DNS 解析漂移（节点域名 TTL/轮换节奏） | 本地递归解析日志 | 半离线：无需抓包，但需开 DNS 查询日志 |

注：F1/F3/F5/F7/F8 中，**F3/F5/F7/F8 在用户侧（自家出口）即可观测**——这正是 MVP Phase C 选 NetFlow 的原因；F2（源分散度）只有机房/云厂商侧能看到，属于「机场对家」的视角，本项目永远拿不到，也不该拿。

### 2.3 流量观测的最小部署形态（按侵入度排序）

| 部署形态 | 能看到 | 看不到 | 部署成本 |
|---|---|---|---|
| **A. NetFlow/sFlow 导出**（家用路由 OpenWrt + softflowd/fprobe → 本地 nfcapd/GoFlow2） | 五元组、包数/字节数、起止时间 → 可算 F1/F3/F5/F6/F7/F8、目的 IP 基数 | 无 payload、无 TLS 指纹、无包长序列 | 一台路由器 + 一个 collector 进程，零抓包 |
| **B. 家用路由镜像（switchport mirror / 端口镜像到一台分析机）** | A 的全部 + 完整包 → Zeek 可出 conn.log/dns.log/ssl.log（JA3/JA4、SNI、证书链）、包长序列、IAT | 解密内容（不需要也不应做） | 一台旁路分析机；Zeek 约 1 核/250Mbps |
| **C. 被动 tap（物理分光/镜像交换机）** | 同 B，且更难被绕过 | 同 B | 硬件成本最高，家用场景收益低于 B |
| **D. 端点侧代理日志**（Clash/sing-box 自身 API） | 每连接五元组+字节量+规则命中——**最便宜**，等价 A 的大部分特征 | 无包级信息 | 零新硬件，读现有面板 API |

推荐路径：**D（零成本起步）→ A（NetFlow 正式化）→ B（需要 TLS 指纹时再上 Zeek）**。C 在家庭场景无必要。

## 3. 业界与学术方法对照

（依据：内部调研文档《华为云机场流量主动识别-方案总纲》《report-vpn-proxy-detection》《加密流量识别-代理隧道检测-学术调研》《云平台识别机场VPN服务-信号与合规边界》，2026-10-14；下述文献细节以该调研的引注为准。）

### 3.1 GFW 式主动探测与被动块判定

- 主动探测：IMC 2015 起系统化；IMC 2020 实测 SS 服务端两阶段检测（被动首包长度+熵筛 → 7 类探测重放），51,837 次探测、>75% 源 IP 被反复探测、探测源集中于 AS4837/4134/17622、NR2 探测长度恒为 221 字节。
- 被动块判定（2021-11 部署的逐 bit 密度检验）：对首个 TCP 载荷包做置位密度检验（popcount/len ≤3.4 或 ≥4.6 bits/byte 落封锁区），**不是 Shannon 熵**；1/4 概率触发、180 秒三元组残留、仅监控约 26% 连接、误伤约 0.6% 正常流量；2024-04 按 SNI 封 QUIC、2025-08 对 TCP 443 无条件 RST。
- 五条豁免规则取反即检测器：popcount 密度、前 6 字节可打印、可打印占比、连续可打印段、TLS/HTTP 指纹匹配。
- **对本项目的含义**：这套是**审查者视角**，作用在「被翻墙的链路」上；我们是**用户侧画像**，目标不同。它的可取之处是把「置位密度/可打印性」从玄学变成了可复现的机械判据——Phase C 若上 Zeek 可以顺带记录，但**不做任何主动探测**（对自家节点发探测包既是规避对抗行为，也可能触发机场风控，见 §4）。

### 3.2 加密流量分类（ML 线）

- 演进：DeepPacket(2017) → DF/DeepFingerprinting(CCS'18, Tor>98%；WalkieTalkie 防御下降到 49.7%) → Var-CNN(PETS'19) → Tik-Tok(PETS'20, 98.4%) → ET-BERT(WWW'22, ISCX-VPN F1 98.9%) → YaTC(AAAI'23) → Flow-MAE(RAID'23) → NetMamba(2024, 六数据集约 99%, 推理快 60×) → TrafficFormer(S&P'25) → NetMamba+(2026, F1+6.44%)。
- 数据集现实：ISCXVPN2016（28GB、14 类）之后，**2023 年后无公开专用代理数据集**；Self-shadow 协议（Snowflake DTLS）6500+ 握手可 100% 区分；标签来源审计是普遍短板（arXiv 2609.02140）。
- **对本项目的含义**：SOTA 模型都是「有标签大流量 + GPU」的游戏。家庭场景日均流量撑不起训练集，**不自训模型**；若未来要上 ML，直接用预训练模型（NetMamba/TrafficFormer 权重开源）做推理，特征给到「流级」即可。

### 3.3 TLS/协议指纹

- JA3 已停维护 → JA4/JA4+ 家族（排序扩展抗乱序；JA4T/JA4TS 可对抗 uTLS 伪装——「穿浏览器 TLS 外衣但 OS 口音不对」）。
- TLS-in-TLS 检测（USENIX Sec'24, Xue et al., pp.2689–2706）：协议无关、抗随机填充与多层封装、ISP 规模百万级验证——**证据等级最高的流量层检测**，原理是外层加密流里出现内层 TLS 握手的包长/时序轮廓。
- Cisco ETA：SPLT（每包载荷长度序列+包间毫秒序列）+ TLS 特征 + IDP（首包 URL/DNS）→ NetFlow → 监督 ML，字段级公开；Palo Alto/Sandvine 算法未公开（专利 US20200274815A1、US20230198911）；Fortinet 官方声明封代理仅 "best effort"。
- 服务端侧指纹：Reality/uTLS 抗 JA3；3x-ui 新版已随机化路径；Marzban 面板 8000 端口、订阅端点路径、面板 favicon mmh3 可被 FOFA/Shodan 检索——这些属于「扫描他人服务」的范畴，本项目明确不做（§4）。

### 3.4 已知误用判据（避坑清单）

- 端口 2052/2053/2082/2083/2086/2087/2095/2096 是 **Cloudflare 备用端口**，非 V2Ray 专用；
- 3x-ui 新版已随机化访问路径，「/panel 固定路径」判据失效；
- 自签证书单独≠代理（IoT/内网也在用）；
- 易误报对象：企业 VPN/SD-WAN、CDN 回源、备份同步、爬虫、游戏加速、API 网关——画像库规则必须带这些负样本。

## 4. 合规与风险边界

**本项目的边界（本文与后续 MVP 都严格遵守）：**

1. **只对自家订阅节点做画像**：数据来源仅限本项目已抓取的快照/告警；不访问、不购买、不爬取任何第三方订阅。
2. **不对外扫描**：不对任何 IP/域名发起端口扫描、指纹探测、面板探测（FOFA/Shodan 检索别人面板 favicon 也属于此列，不做）；不发送任何主动探测包（GFW 式重放、TLS 探针一律不用）。
3. **不做规避对抗**：不研究如何让自家流量躲过检测；流量观测的唯一目的是**验证自家订阅节点的连通性与画像准确性**，不涉及帮助任何流量绕过审查。
4. **数据不出本地**：节点 server/域名/IP/RDAP 结果只落在本地 `data/` 与仪表盘；调研只向外发送公开文献检索词，任何情况下不把本机数据、订阅 URL、token、机场账号发到外部。
5. **隐私最小化**：交付物与日志中 IP 末字节掩码；快照中的 password 字段永不输出；仪表盘展示聚合统计而非逐节点明细（个人使用场景下可例外，但导出物默认脱敏）。
6. **观测对象限于自家设备**：NetFlow/Zeek 只部署在自家出口，只看自家流量的元数据；不解析/不解密任何内容，不留存 payload。

**法律背景（仅作边界说明，不构成法律意见）**：在中国大陆，「经营/销售」翻墙服务有刑事风险（刑法 285 条 3 款，有 4 年 6 个月+罚金 50 万的判例）与行政案例（没收违法所得等）；个人使用端案例多为行政处罚（国际联网暂行规定第 6/14 条，责令停止+警告+罚款）。本文的全部内容限定在**自家订阅的安全画像与连通性验证**，不构成任何经营行为的建议。检测/画像信号（尤其流量侧）只能做线索聚合与人工复核，不能单独定性任何结论。

## 5. 结论与 MVP

### 5.1 这个方向值不值得做？

**值得，但要换叙事。**

- 「识别机场」作为目标太大且越界风险高；落地后真正有价值的命题是三个：
  a. **资产画像**：某个 server/IP/域名是不是机场基建（离线层，已验证可行，§1.10 前四项联合即可）；
  b. **连通性验证**：该节点此刻是否真的在转发自家流量（流量观测层，Phase C）；
  c. **异常检测**：自家订阅里混入的占位节点/失效节点/换血节点（§1.7 已可直接做）。
- 华为云签名路线**在节点侧证伪**——这本身就是重要产出：纠正了「机场=华为云」的先验，真实画像是「AWS≈30% + 腾讯/百度/GCP/Oracle + 少量批发 maintainer（netutils-mnt、ACEVILLE、DoD NIC）」。画像库应该按 **org/ASN 频次表** 持续学习，而不是按厂商白名单。

### 5.2 MVP：三阶段

**Phase A · 纯离线画像库（2–3 人日，立即可做）**

- 新建 `signatures/idc-profile.yaml`：从现有快照统计 top-N RDAP org / ASN / CIDR（Baidu Noc、netutils-mnt、ACEVILLE、HINET、DoD NIC、James Tian、AWS ap-se/ap-ne、Tencent、Google…），附「出现机场数」「首次/最近出现时间」字段；
- 在现有 alerts 管道（`huawei.yaml` 旁）加 idc 匹配 + 三个新指标：**单 IP 扇出系数、高位端口占比、伪 TLD/占位节点占比**；
- 仪表盘（衔接 docs/05）每机场加四卡：IDC 集中度 / 扇出 Top3 IP / 假节点数 / churn 率；
- 占位节点过滤规则（§1.7）直接进 alerts 降噪。
- 工作量：脚本 1 天 + 仪表盘 1–2 天。

**Phase B · DNS 被动观测（3–5 人日，仍不抓包）**

- 本地递归解析（dnsmasq/unbound）开查询日志，记录节点域名 TTL/解析漂移；定时任务对快照内域名做本地解析 diff；
- 产出：域名轮换周期表 → 补全「域名侧扇出」（对靠域名轮换的机场，等价于 §1.3 的 IP 扇出）。
- 工作量：3–5 人日（含观测窗口等待时间）。

**Phase C · NetFlow 流量验证（5–10 人日，需一台家用路由）**

- OpenWrt + softflowd → GoFlow2/nfcapd 本地 collector；对自家出口流做 F1/F3/F5/F7/F8 五特征打分；
- 对照组：B 站/淘宝/Cloudflare 等正常流量，验证「机场节点流量」与「普通 HTTPS」在五特征上的可分性（方案总纲评分卡可直接借用权重）；
- 可选升级：同机跑 Zeek 出 JA4/SNI，验证节点自述协议与实际 TLS 指纹一致性；
- 工作量：collector 2–3 天 + 特征打分 2–3 天 + 观测调参 2–4 天。

**总工作量：约 3 人周**（Phase A+B 可一周内完成并上线纯离线版；Phase C 依赖硬件与观测窗口）。

### 5.3 明确不做

- 主动探测自家以外的任何服务（含 GFW 式重放、端口扫描、面板指纹检索）；
- 训练 ML 模型（数据量不支持；如需，用开源预训练权重推理）；
- 任何「让流量更难被识别」的研究或配置；
- 向任何外部服务发送节点数据。
